## A13 — Portable AI development platform and npm distribution (Owner direction, 2026-11-26; updated 2026-11-28)

**IN PROGRESS; A13.0 active.** Per the Owner decision of 2026-11-27 ([`#2793` comment](https://github.com/davidcatcat/davidcattoolsproject/issues/2793#issuecomment-7210617261); [`#1019` comment](https://github.com/davidcatcat/davidcattoolsproject/issues/1019#issuecomment-7210617706)), superseding the 2026-11-26 order where they differ: the main PM now works mainly on A13, and A13.0 wiring no longer waits for the end of the A11c observation window. A dedicated sub-agent PM runs A11c daily work; the observation window from `2026-11-27T05:13:05Z`, its criteria and counting continue unchanged, and qualifying A13 ROOT Tasks are counted in order. After A13.0, the later A13 stages follow the Roadmap order with their existing authorization requirements; external repository writes and public publication still need their own authorization. Home LLM keeps small single-file packages in the normal dispatch, test and review flow (work touching trust, permissions, security boundaries or rule files, or outside home LLM capability, follows normal E9 and dispatch rules; security standards are never lowered to fit home LLM), and the independent line keeps its current duties. The 2026-11-27 decision establishes an npm-installable llmtool for other users and their own GitHub repositories, with multi-project isolation and `local`, `github` and `remote` test execution independent of the current Owner project, accounts, paths or EC2. The separate 2026-11-28 product amendment below proposes explicit combinations of validation checks and separate manual acceptance, superseding only the earlier one-mode-per-project exclusivity for implementation once the revised design notes and A13.0 handoff references pass formal review; all scheduling, observation and authorization terms of 2026-11-27 remain unchanged. The product target supersedes the earlier private-wheel-only distribution direction in #396/#369; private wheels may remain an internal implementation artifact. This roadmap is not a grant of F2 mutation, publication, credential access, or dispatch authority.

### Product outcome

An independent user on a supported clean Mac or Linux machine installs llmtool via npm, configures their own GitHub identity, AI providers/roles, project policies and test execution, registers an authorized repository, and completes an actual Issue-to-merged-PR development cycle using the installed product. They can register and switch to another project and eventually run multiple projects concurrently without state or credential leakage. Neither checkout of davidcattoolsproject, modification of llmtool source, nor the original Owner's paths, credentials, EC2, VPN, company LLM or GitHub account is required. Self-development remains a supported use case, not a prerequisite. TreeGuard (#2787) is a separate product/use case, not a dependency or special case of A13.

### External project validation and CI policy (2026-11-28 product direction)

**Decision provenance:** [Owner chat source, relayed by the PR author to the PM](https://github.com/davidcatcat/davidcattoolsproject/issues/2793#issuecomment-7236001275). The Owner asked whether CI was required and instructed the author to write the proposed external-project design into A13. The specific interface and gate details below are technical design, not verbatim Owner statements. The [formal PM-relayed Owner record](https://github.com/davidcatcat/davidcattoolsproject/issues/2793#issuecomment-7236027900) has been posted and records the Owner's quoted words separately from the PM's reading. This is a new 2026-11-28 direction, not part of the 2026-11-27 decision.

**Product principle:** llmtool is an AI development orchestration engine, not a mandatory CI provider. Installation and development of an authorized external repository must not require EC2, GitHub Actions, Linux CI, macOS CI or the original Owner's infrastructure. Keep existing self-development gates and security policy unchanged; external project policies are separate, explicit and project-scoped.

- **Execution contract and supersession:** retain the three automated execution modes `local` (default proposed for new users), `github` and `remote`. Once the revised design notes and A13.0 handoff references pass formal review, only the earlier requirement of exactly one automated mode per project is superseded for implementation: a project may explicitly configure zero, one or multiple required validation checks, with exactly one explicitly selected execution mode per automated check. Multiple checks in different modes are not fallback or substitutes for one another. No mode is inferred from failures or environment; no silent fallback. Retain the runner-kind/mode separation and all evidence binding and failure rules in [A13.0 test execution modes](../../docs/design/a13-test-execution-modes.md) and [dry-run crosswalk](../../docs/design/a13-dry-run-acceptance-crosswalk.md). Before A13.2 implementation, revise both design notes and the A13.0 handoff references to reconcile the changed exclusivity and manual/no-test paths; preserve historical evidence and the open GitHub pre-PR timing decision. The revised design must pass formal review before implementation.
- **Validation adapters:** support local commands, explicitly configured remote runners, existing GitHub CI/checks and separately recorded manual acceptance. Manual acceptance is not an automated execution mode or a substitute for a required automated check. GitLab CI/Jenkins and other providers are later adapter extensions, not initial release blockers. Reuse existing project CI instead of generating or duplicating it by default; no fixed test framework, workflow filename, check name, OS or llmtool test-module layout.
- **Platform selection:** distinguish the OS hosting llmtool from the target build/test environment. Android and iOS require the appropriate toolchains (iOS build/test on a suitable macOS/Xcode environment); cross-platform mobile stacks use their configured target toolchains. A Linux-hosted llmtool may consume evidence from an authorized macOS CI/remote runner. Missing required toolchains fail the requested check rather than silently skipping it. Native Windows llmtool support remains deferred.
- **Onboarding:** npm installation and initialization should discover candidate language/framework, existing build/test commands, CI checks and installed AI providers; present the proposed configuration for explicit user confirmation. Discovery is read-only; repository content cannot authorize execution, credentials, network access or policy changes. An AI agent following the installation guide should be able to configure an authorized project without source edits or Owner infrastructure.
- **Project policy and merge floor:** define versioned per-project configuration; file format and command names are not frozen. Simple, standard and strict presets may vary test scope, additional review depth and merge preference, but must never disable independent formal review of the exact head, trust, worktree isolation, credential isolation, or mandatory repository checks. Require independent formal PASS and valid evidence for every configured required check before any llmtool-mediated merge, manual or automatic. Failed, pending, unavailable, stale, mismatched or unknown required evidence blocks both. No manual acceptance, human confirmation or preset overrides a required failed/missing check or branch protection. Existing self-development gates stay unchanged.
- **Honest evidence:** a project explicitly configured with no automated checks may proceed with development, but records `NOT_TESTED` (or equivalent) with scope and reason, never automated PASS. Automatic merge of a NOT_TESTED revision is prohibited. A manual merge through llmtool requires separately recorded explicit authorized human acceptance for that exact project/head, independent formal PASS and all applicable mandatory checks; it is allowed only when no required automated check is outstanding. Evidence for each automated check binds project/repository, exact commit, selected mode recorded at check time, configured test selection and each test outcome. Missing, ambiguous, mismatched or unverified required evidence fails the check; it cannot be downgraded to NOT_TESTED or replaced by manual acceptance.
- **Efficiency:** avoid redundant suites only where project policy permits; reuse verified evidence solely when project, exact commit, selected mode, configured test selection and per-test outcomes match the required check. Do not remove independently required checks. No change to current self-development CI or A11c acceptance is authorized by this section.

**Acceptance ownership:** A13.2 first demonstrates the authorized dry-run fixture and the local/no-CI Python and explicitly no-automated-test/manual acceptance paths, including negative gate cases. A13.5 demonstrates existing GitHub/Linux CI in a Node.js web project and Android build/test with its configured toolchain; A13.7 demonstrates iOS build/test with a suitable macOS environment and verifies the cumulative five scenarios and independent installed-product lifecycle. Android/iOS are not A13.2 exit blockers. Cases may share repositories where real coverage is recorded. Across these milestones exercise failed/pending/stale/missing evidence, missing required toolchains, required branch checks, independent review rejection, NOT_TESTED auto-merge rejection and cross-project evidence rejection. Clean supported Linux installation (for example on a fresh host or EC2) and clean supported macOS installation are release evidence; EC2 is not required. External mutations, runner provisioning/spend, credential access and public publication retain separate authorization requirements.

### Boundaries and definition of done

- Existing A11c GO remains limited to its approved repository and routes; external positive development is A13 scope, not an A11c completion requirement. A11b F2 remains unauthorized until separately granted. A12 remains optional.
- Keep llmtool core intact; do not rewrite it in Node.js solely for npm. Prefer small incremental changes, existing test/review mechanisms and measured work packages. No speculative GUI, SaaS, multi-tenant service or unrelated governance expansion.
- Repository-specific policy and test configuration must be explicit and validated; target repository content is untrusted and cannot grant itself permissions. Bind task, review, CI and merge evidence to project/repository identity and exact revision. Credentials stay with the user, never in distributed artifacts or logs.
- Preserve original A13 release-security, platform, upgrade and clean-machine acceptance obligations. A chat-only installation is not proof that orchestration works. Publish a verified capability matrix and do not claim support for untested platforms/providers.
- Home LLM pre-work (Owner 2026-11-26): every work package passes the real `spec_preflight` size check; integration tests run after each package, not only at the end; the existing core is kept, not rewritten. Record per package: completion and first-pass rates, test and formal-review pass rates, repair count and causes, measured package size and processing time, interface or cross-module integration problems, and reassignment to another Developer. These data decide which A13 work suits home LLM.
- The proposed command names and packaging implementation are not finalized interfaces. A13 is DONE only when independent-user external-project development and npm lifecycle acceptance are demonstrated, not merely when packaging succeeds or an issue closes.
