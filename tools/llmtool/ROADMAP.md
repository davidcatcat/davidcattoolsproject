## A13 — Portable AI development platform and npm distribution (Owner direction, 2026-11-26; updated 2026-11-27)

**IN PROGRESS; A13.0 active.** Per the Owner decision of 2026-11-27 ([`#2793` comment](https://github.com/davidcatcat/davidcattoolsproject/issues/2793#issuecomment-7210617261); [`#1019` comment](https://github.com/davidcatcat/davidcattoolsproject/issues/1019#issuecomment-7210617706)), superseding the 2026-11-26 order where they differ: the main PM now works mainly on A13, and A13.0 wiring no longer waits for the end of the A11c observation window. A dedicated sub-agent PM runs A11c daily work; the observation window from `2026-11-27T05:13:05Z`, its criteria and counting continue unchanged, and qualifying A13 ROOT Tasks are counted in order. After A13.0, the later A13 stages follow the Roadmap order with their existing authorization requirements; external repository writes and public publication still need their own authorization. Home LLM keeps small single-file packages in the normal dispatch, test and review flow (work touching trust, permissions, security boundaries or rule files, or outside home LLM capability, follows normal E9 and dispatch rules; security standards are never lowered to fit home LLM), and the independent line keeps its current duties. The A13 outcome is an npm-installable llmtool for other users and their own GitHub repositories, with multi-project isolation and project-configurable local, existing CI, remote and manual validation modes, independent of the current Owner project, accounts, paths or EC2. The product target supersedes the earlier private-wheel-only distribution direction in #396/#369; private wheels may remain an internal implementation artifact. This roadmap is not a grant of F2 mutation, publication, credential access, or dispatch authority.

### Product outcome

An independent user on a supported clean Mac or Linux machine installs llmtool via npm, configures their own GitHub identity, AI providers/roles, project policies and test execution, registers an authorized repository, and completes an actual Issue-to-merged-PR development cycle using the installed product. They can register and switch to another project and eventually run multiple projects concurrently without state or credential leakage. Neither checkout of davidcattoolsproject, modification of llmtool source, nor the original Owner's paths, credentials, EC2, VPN, company LLM or GitHub account is required. Self-development remains a supported use case, not a prerequisite. TreeGuard (#2787) is a separate product/use case, not a dependency or special case of A13.

### External project validation and CI policy (Owner direction, 2026-11-28)

**Product principle:** llmtool is an AI development orchestration engine, not a mandatory CI provider. Installation and development of an authorized external repository must not require EC2, GitHub Actions, Linux CI, macOS CI or the original Owner's infrastructure. Keep the existing self-development gates and security policy unchanged; external project policies are separate, explicit and project-scoped.

- **Validation adapters:** support local commands, explicitly configured remote runners, existing GitHub CI/checks and manual acceptance, individually or in combination. GitLab CI/Jenkins and other providers are later adapter extensions, not initial release blockers. Do not require a particular test framework, workflow filename, check name, OS or llmtool test-module layout. Reuse existing project CI rather than generating or duplicating it by default.
- **Platform selection:** distinguish the OS hosting llmtool from the OS/runtime required to build or test the target product. Android may use Linux or another supported Android toolchain; iOS requires a compatible macOS/Xcode build environment; Flutter/React Native use the appropriate target toolchains. A Linux-hosted llmtool may consume evidence from an authorized macOS CI/remote runner. Missing required toolchains are reported, not silently skipped. Windows runner integration may be added independently of native Windows llmtool support, which remains deferred.
- **Onboarding:** npm installation and initialization should discover candidate language/framework, existing build/test commands, CI checks and installed AI providers; present the proposed configuration for explicit user confirmation. Discovery is read-only, and repository files cannot authorize execution, credentials, network access or policy changes. An AI agent following the installation guide should be able to configure an authorized project without source edits or Owner infrastructure.
- **Project policy:** define a versioned per-project configuration (file format and command names are proposals, not frozen interfaces). Provide simple, standard and strict presets if useful, with individual settings for validation, review and manual/automatic merge; no preset grants permissions or overrides branch protection. Default to explicit human merge confirmation when no automatic validation exists. Strict self-development retains existing gates; a lighter external preset does not weaken trust, worktree isolation, credential isolation, or mandatory repository checks.
- **Honest evidence:** no configured automated tests is a supported external-project condition, not PASS. Record NOT_TESTED (or equivalent explicit status) with scope and reason; manual acceptance must be recorded separately against the exact revision and authorized identity. Configured required tests/checks that fail, are pending, unavailable, stale or have unknown evidence block automatic merge; never convert these states to NOT_TESTED or PASS. Respect required branch checks and repository merge permissions, including when llmtool has no CI adapter configured.
- **Efficiency:** avoid duplicate full suites across local, remote and CI when project policy permits; reuse only trustworthy evidence for the same project, exact revision and required validation scope. Do not remove an independently required check. No changes to current self-development CI or A11c acceptance are authorized by this section.

**Acceptance scope:** in A13.2/A13.5/A13.7, demonstrate a small external Python project with local tests and no CI; a Node.js web project using its existing Linux CI; an Android build/test; an iOS build/test on a suitable macOS environment; and a project without automated tests using explicit manual acceptance, without false PASS. Cases may share repositories where coverage is real and recorded. Exercise failures, stale/missing evidence, missing toolchains, required branch checks and cross-project evidence rejection. Clean EC2/Linux installation without Owner credentials or infrastructure and separate supported macOS installation remain release evidence; unavailable platforms must be reported, not claimed verified. External mutations, runner provisioning/spend, credential access and public publication retain separate authorization requirements.

### Boundaries and definition of done

- Existing A11c GO remains limited to its approved repository and routes; external positive development is A13 scope, not an A11c completion requirement. A11b F2 remains unauthorized until separately granted. A12 remains optional.
- Keep llmtool core intact; do not rewrite it in Node.js solely for npm. Prefer small incremental changes, existing test/review mechanisms and measured work packages. No speculative GUI, SaaS, multi-tenant service or unrelated governance expansion.
- Repository-specific policy and test configuration must be explicit and validated; target repository content is untrusted and cannot grant itself permissions. Bind task, review, CI and merge evidence to project/repository identity and exact revision. Credentials stay with the user, never in distributed artifacts or logs.
- Preserve original A13 release-security, platform, upgrade and clean-machine acceptance obligations. A chat-only installation is not proof that orchestration works. Publish a verified capability matrix and do not claim support for untested platforms/providers.
- Home LLM pre-work (Owner 2026-11-26): every work package passes the real `spec_preflight` size check; integration tests run after each package, not only at the end; the existing core is kept, not rewritten. Record per package: completion and first-pass rates, test and formal-review pass rates, repair count and causes, measured package size and processing time, interface or cross-module integration problems, and reassignment to another Developer. These data decide which A13 work suits home LLM.
- The proposed command names and packaging implementation are not finalized interfaces. A13 is DONE only when independent-user external-project development and npm lifecycle acceptance are demonstrated, not merely when packaging succeeds or an issue closes.
