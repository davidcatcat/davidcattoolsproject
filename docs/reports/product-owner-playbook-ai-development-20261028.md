# Report C — Owner Playbook：以最少管理負擔取得可用產品（v3）

- **日期：** 2026-10-28　**Snapshot：** `139a62c0483560be4e7a0aadd76c82652a8a2cd9`
- **對象：** 本專案的 Owner（需求方、出資者、最終決策者）與 AI 團隊。
- **依據：** [Report A（技術稽核）](full-repository-technical-audit-20261028.md)、[Report B（演變與決策回顧，含 9A AI Management Failure Register）](project-evolution-decision-retrospective-20261028.md)。
- **版本：** v3。v1／v2 把需求分析、驗收標準、Scope、停損、技術提案判斷等工作寫成 Owner 的責任，這是錯誤前提，已撤銷。本版核心原則：**讓 Owner 以最少的管理負擔，取得高品質的產品交付；日常產品管理、工程管理、技術品質與交付管理由 AI 團隊主動承擔。**
- 本文全部為建議。涉及既有 Gate、Reviewer 配對、Dispatch 政策或 Roadmap 的項目標 **OWNER_DECISION_REQUIRED**，採用與否由 Owner 決定；AI 不得據此直接改政策。文中數字皆為待驗證目標。

---

## 1. 責任分工總表

| 類別 | 誰 | 負責什麼 | 不負責什麼 |
|---|---|---|---|
| **A. Owner 必須親自決定** | Owner | 產品方向與定位；一個 NOW；預算上限；安全與資料外送邊界；新帳號／新付費服務；看 demo 後說符合／不符合；AI 明說能力不足時決定替代方案 | 技術架構、模組設計、工作包拆解、PR 順序、CI 策略、worktree、Agent 交接、催 PM、找架構缺陷、寫技術規格、QA／CI 驗證 |
| **B. AI PM 主動完成** | PM session | 把 Owner 的每句話轉成需求確認單；MVP 與範圍；新想法影響分析；Roadmap；驗收標準；每週 demo；週報；需求變更影響 | 不得把需求原樣展開成實作；不得把技術狀態呈現為 Owner 決策 |
| **C. AI CTO／Architect 主動完成** | 同一 PM session 或獨立 session | 每個架構／治理提案附三選項（含不做）、最小版本、停損；過度工程預警；技術債、容量、成本看板；對 PM 與 Owner 說「不建議，因為…」 | 不得只回答「可以實作」 |
| **D. AI Engineering 自動完成** | 驅動器＋Developer＋Reviewer | 派工、測試、審查、修復、合併、worktree 退場、額度改派、CI 選擇、事件消費 | 不得經 Owner |
| **E. 只有重大例外才通知 Owner** | PM | 預算超標；安全事件；同一問題兩次修復失敗；需要新帳號／新支出；AI 能力不足以完成某項工作；Owner 定義的方向與現況衝突 | 其餘不通知 |

不一定需要四個獨立 AI。最小配置：一個 PM session 同時承擔 B 與 C，但 C 的輸出格式（第 4 章）是硬性要求；D 由確定性程式承擔；Reviewer 加「可用性驗收」。

**責任類型區分：** 專業建議責任（B、C）、決策權（A）、執行責任（D）、品質保證責任（D 的 Reviewer＋B 的驗收標準）、最終授權責任（A，僅限 A 列出的事項）。

## 2. Owner 要做的四件事（全部）

1. **宣告一個 NOW。** 一句話，例如「現在只做一條鏈 E2E」。其餘由 AI PM 標 FROZEN。（本身為 OWNER_DECISION_REQUIRED，也是唯一需要 Owner 的 Roadmap 決策）
2. **設預算上限。** 每月 token／CI／雲一個數字。額度用盡由 AI 在 ALLOWED 路線內處理；超上限才找你。
3. **每週看一次 demo。** AI PM 交一個可操作的東西；你操作後只回答「符合／不符合／哪裡不符合」。做不出 demo 是 PM 的失敗。
4. **只接受決策單。** AI 要你決定任何事，必須用第 5 章格式；不符格式直接退回「請用決策單」。

此外，**明說委託模式**一次：對每類事情說「你們決定」或「問我」；AI PM 寫成分工表後不再逐條問。

## 3. AI PM 的硬性輸出格式

### 3.1 需求確認單（Owner 每說一個想法，PM 先回這個，不先排程）

```text
你說的是：<一句話重述>
我理解的情境：你在 <時刻> 想要 <結果>，現在只能 <現況>
這是：正式需求 / 想法（我先記著）/ 回報問題
驗收：你會 <操作>，看到 <結果> 就算完成
不做：<我判斷不在範圍的事>
影響：做它會延誤 <NOW 的哪一步> 約 <多久>；建議 現在做 / NEXT / FROZEN
需要你決定嗎：否（我照建議做）/ 是（附決策單）
```

歷史對照：10-19「開放 worktree 吧，但是要判斷什麼時候做完改刪除了」若經此單，PM 應回「驗收：PR 合併後 worktree 自動消失；不做：不寫超過一頁的規範」，而不是 13 KB 規範。

### 3.2 週報（一頁，第一行是 NOW 的可用進度）

```text
NOW：<項目>；本週你能操作的東西：<有／無；怎麼操作>
demo：<時間／方式>
成本：Codex tokens、Reviewer 輪數、Mac／EC2 分鐘、我的手動命令數
容量：ACTIVE worktree、磁碟剩餘
例外（需要你）：<決策單連結或「無」>
下週 NOW：
你需要做：無 / <一個動作>
```

### 3.3 「這個 TUI 不好用」類回報的處理

Owner 只需說這一句。PM 必須自行：重現、對照已知缺陷、列出缺的使用者功能、對照 Roadmap、提出改進與驗收，再以需求確認單回 Owner。**不得要求 Owner 寫 UI 規格。**

## 4. AI CTO 的硬性輸出格式

### 4.1 方案比較單（任何架構／治理／路線提案都必須附）

| 選項 | 解決什麼 | 不解決什麼 | 成本（人日／token／CI） | 風險 | 對 NOW 影響 | 最小版本（可在幾天內看到真實執行） | 停損 |
|---|---|---|---|---|---|---|---|
| A（建議） | | | | | | | |
| B | | | | | | | |
| C 不做／延後 | | | | | | | |

沒有「不做」選項、沒有最小版本、沒有停損的提案，PM 不得排程。

### 4.2 過度工程預警（CTO 主動觸發，不等 Owner 發現）

觸發任一即在週報「例外」欄報告並附方案比較單：
- 新增一份超過兩頁的規範或契約。
- 新增第二套做同一件事的機制（授權、上限、Worker 描述）。
- 新增一條 AI 路線／模型／帳號而主鏈未通。
- 一個 runtime 功能上線後持續 0 使用。
- 單一模組行數、政策文件體積、worktree 數、磁碟用量超過 CTO 自訂且公告的基準。

歷史對照：F1 Git 容器化、S1b／B fake-only、五套授權、High Debug 都會在此被攔下。

### 4.3 「不建議」的說法

AI 對 Owner 的技術想法，必須能說：「不建議，因為 <風險>；更好的是 <方案>；若你仍要做，代價是 <延誤什麼>。」只回答「可以實作」視為失職。

## 5. Owner 決策單（AI 唯一可以向 Owner 要決策的格式）

```text
要決定：<一句話>
為什麼需要你：預算 / 方向 / 安全或資料外送 / 新帳號或支出 / AI 能力不足（五選一）
推薦：<方案>，因為 <一句話>
替代：<方案 B> / 不做
優缺點與風險：A：<一行>；B：<一行>
不決定的後果：<一行；含等待多久會自動採推薦方案>
請回答：是 / 否 / A / B
```

不符合此格式的決策請求，Owner 應退回。技術細節放附錄，不放決策單正文。

## 6. AI Engineering 自動完成的事（Owner 不參與）

- 派工、測試、審查、修復、合併：由驅動器推進；PM 只處理 BLOCKED。
- 額度／CLI 不可用：技術狀態，PM 在 ALLOWED 路線內改派（OWNER_DECISION_REQUIRED：dispatch 規則的使用方式）。
- worktree 退場：通過 D6 lifecycle gate 的自動退場；RETAIN_BLOCKED 由 PM 處理。
- CI 範圍、merge 方式、Reviewer 復用：由 PM／CTO 在現行授權內評估；改變 Gate 者走決策單（OWNER_DECISION_REQUIRED）。
- 容量與成本看板：CTO 自動產出，週報引用。

## 7. 例外通知的門檻（E 類）

| 情況 | 通知方式 |
|---|---|
| 預算超標或預估超標 | 決策單 |
| 安全事件、資料外送疑慮 | 立即，決策單 |
| 同一 root cause 兩次修復失敗 | 週報例外欄（AI 自行走 High Debug 等既有規則，不問 Owner） |
| 需要新帳號／付費服務／root 權限 | 決策單 |
| AI 能力不足（例如無法無人值守連續運作） | 決策單，附替代管理機制 |
| NOW 與現況衝突（例如新發現使 NOW 不可行） | 決策單 |

其他一切不通知。

## 8. 驗收：誰驗什麼

| 層 | 誰 | 驗什麼 |
|---|---|---|
| 程式正確 | Developer 自測＋Reviewer | diff、測試、CI |
| **使用者可用** | **AI QA／Reviewer（新增）** | 依需求確認單的「驗收」句實際操作一遍，附操作紀錄；未做此步不得標 DONE |
| 符合期望 | Owner | 看 demo，回答符合／不符合 |

「MERGED ≠ VERIFIED」由 AI QA 負責把 VERIFIED 做出來，不由 Owner 補。

## 9. 避免重複過去錯誤的對照表（AI 自檢，不是 Owner 檢）

| 過去模式 | 觸發訊號 | AI PM／CTO 必須做 |
|---|---|---|
| 一句話變框架 | Owner 一句話 | 先回需求確認單與最小版本 |
| 先建框架後驗證 | 提案含 contract／gate／fake／offline | 方案比較單＋停損＋真實執行日期 |
| 額度變決策 | 「X 的上限到了」 | 自動改派，週報記一行 |
| 開新路線 | 「可以試 Y」 | 影響分析：主鏈通了嗎、延誤什麼 |
| PR 當進度 | 週報只有 PR 數 | 重寫為「你能用什麼」 |
| 文件膨脹 | 新增超過兩頁 | CTO 預警，先刪再加 |
| 容量無人管 | worktree／磁碟上升 | 看板＋自動退場 |
| 修工具的工具 | 「需要 helper 檢查 helper」 | 問「擋住哪個已發生事故」 |

## 10. 建議立即實施的五項（對 AI 團隊；Owner 只需確認第 1 項）

1. Owner 宣告 NOW＝一條鏈 E2E（OWNER_DECISION_REQUIRED，也是唯一需要 Owner 的項目）。
2. PM 自本週起用需求確認單、週報、決策單三種格式；不符格式的輸出視為未完成。
3. CTO 自本週起對任何提案附方案比較單；建立容量與成本看板。
4. Engineering 以驅動器取代手動串接；Reviewer 加可用性驗收。
5. 下週 demo：Owner 在 TUI 提一個需求，看到它被開發、審查、合併、顯示完成。做不到是 PM 的失敗，不是 Owner 的。
