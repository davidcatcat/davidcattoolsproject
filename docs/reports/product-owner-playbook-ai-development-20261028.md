# Report C — Practical Product Owner Playbook for AI-Driven Software Development

- **日期：** 2026-10-28　**Snapshot：** `139a62c0483560be4e7a0aadd76c82652a8a2cd9`
- **對象：** 本專案的 Product Owner。
- **依據：** [Report A（技術稽核）](full-repository-technical-audit-20261028.md)、[Report B（演變與決策回顧）](project-evolution-decision-retrospective-20261028.md)。本文只寫方法與範本，不重複證據；每條建議後括號標註對應的歷史教訓（M1–M14、DEC-xxx）。
- **原則：** 輕量、可直接用於 llmtool、不官僚。整份 Playbook 的核心只有一句話：**你親手驗收，一次只做一條線，AI 的提案先要最小版本。**
- **版本：** v2（2026-10-28 自我校正）。本文全部為建議；凡標 **OWNER_DECISION_REQUIRED** 者涉及既有 Gate、Reviewer 配對、Dispatch 政策或 Roadmap，採用與否由 Owner 決定，PM 不得直接執行。文中數字（週期、門檻）皆為**待驗證目標**，應先量測基準再設定。

## 1. 我的角色與責任

| 我負責 | 我不負責 |
|---|---|
| 產品是什麼、給誰用、怎樣算可用（vision + MVP） | 額度何時用完、哪個 CLI 今天能用（技術狀態） |
| 每週優先順序：只有一個 NOW | 每個 Task 的模型／參數／Reviewer 帳號 |
| 親手驗收：每週一個真實任務 | 審 PR diff、跑測試、讀 CI log |
| 預算上限與安全底線 | 代記每一則 Owner 決策到 GitHub |
| 停損：決定何時停止一條路線 | 選 merge 順序、建 worktree |

**檢查句：** 如果一件事我不做也不會改變產品方向、預算或安全邊界，它就不該到我這裡。（M9、DEC-018／028）

## 2. 如何提出好的需求

### 2.1 需求前五問（提交前自答，缺一不提）

1. 這個功能解決**我在哪個時刻**的什麼問題？（寫一個具體情境，不是功能名）
2. 這是必要（沒有它產品不可用）還是想法？
3. 它和「使用者從 TUI 提需求 → 看到結果」這條主線的關係是什麼？
4. 現有功能能不能做到 80%？（先問 PM：「我們已經有什麼？」）
5. 最簡單的版本是什麼？（M2、DEC-014）

### 2.2 需求範本（貼給 PM 用）

```text
需求：<一句話>
情境：我在 <時刻> 想要 <結果>，現在只能 <現況>。
必要性：必要 / 想法
主線關係：主線 / 支線 / 無關
驗收：我會做 <步驟 1、2、3>，看到 <結果> 就算完成。
不要做：<明確排除，例如：不要新增路線、不要改政策文件>
期限與停損：<日期>；到期沒有真實執行證據就停。
```

**壞例（歷史）：** 「開放 worktree 吧，但是要判斷什麼時候做完改刪除了」→ 13 KB 規範，自動刪除至今未完成（DEC-019）。
**好例（改寫）：** 「允許多個 worktree。驗收：PR 合併後 24 小時內該 worktree 自動消失；本機 ACTIVE worktree 永遠 < 20。不要做：不要寫超過一頁的規範。」

## 3. 如何評估 AI 的技術建議

AI 提案的常見放大模式（Report B 第 9 章）：一句話 → 契約 → gate → 文件 → 從未使用。評估時只問三件事：

1. **最小版本是什麼？** 要求 AI 先給「一天可做、能看到真實執行」的版本。
2. **它取代什麼，還是疊加？** 若是疊加（第二套授權、第三套上限），預設拒絕。（M5）
3. **兩週後怎麼知道它有用？** 要有使用計數或量測；0 使用即移除。（DEC-030）

**紅旗清單**（出現任一就要求重提）：
- 「fake-first」「offline-only」且沒有真實呼叫日期（DEC-014）
- 「為了未來 X 先做 Y」（DEC-009）
- 新增一份 > 2 頁的規範或契約
- 新增一條新的 AI 路線／模型／帳號
- 用「安全」「可靠」當理由但沒有說擋住什麼具體事故

## 4. 如何比較技術方案

### 4.1 三選項規則
任何重大技術決策，PM 必須提供三個選項，其中一個是「不做／延後」，並填：

| 選項 | 解決什麼 | 不解決什麼 | 成本（人日／token／CI） | 風險 | 對主線影響 | 需要 PoC？ | 驗收 |
|---|---|---|---|---|---|---|---|

### 4.2 重大決策範本

```text
決策：DEC-<n> <標題>
日期：
問題：
選項 A / B / C（含「不做」）：
我選：<X>，因為 <一句話>
已知限制：
停損條件：<日期或指標>；觸發則 <回退動作>
量測：<兩週後看什麼數字>
授權範圍：<只允許改哪些檔／模組>；不授權 <…>
```

歷史對照：EC2 offload P0（DEC-029）若有「量測：每 Task Codex prompt tokens 前後比較；停損：兩週未見 20% 下降則降級為 P2」，就不會以「NOT VERIFIED」持續佔 P0。

## 5. 如何判斷 MVP

MVP 只回答一個問題：**我能不能不碰 Codex／Claude CLI，只在 llmtool 裡完成一件真實的小事？**

本專案的 MVP（建議採用，與 Report A 第 19 章一致）：

1. 在 TUI 輸入需求，指定 PM session。
2. PM 記錄決定；llmtool 自動派 Codex 到 D6。
3. 測試在 EC2 跑；Reviewer 自動派；FAIL 自動退修一次。
4. PASS 後 PM 開 PR 並合併；TUI 顯示 COMPLETED。
5. 關閉 TUI 再開，狀態還在。

**不在 MVP：** 第二條 Developer 路線、High Debug、Telegram、Web、他人安裝、gw 真實題。
**MVP 驗收：** 我連續三次用它完成三個不同的小任務。

## 6. 如何設定優先順序

- Roadmap 只有一個 **NOW**，其餘 **NEXT**（最多 3 個）或 **FROZEN**。
- 插隊規則：只有「安全事故」「產品不可用」「預算爆」可以插 NOW；「省錢」「可見性」「新模型」不能。（DEC-029、DEC-025）
- 額度／CLI 不可用 **不改優先順序**，只改派已允許的路線。（M9）
- 每週一次 15 分鐘：確認 NOW 是否仍是 NOW；若連續兩週 NOW 沒有 Owner 可驗收的進展，先問「是不是範圍太大」，再問「是不是路線錯」。

## 7. 如何授權 PM

### PM 預設可自行決定（不必問我）
- Task 拆解、Developer／Reviewer 路線（在已 ALLOWED 集合內）、重試、BLOCKED 隔離、PR 建立與合併（gate 全過）、文件修正、測試範圍、CI 範圍內的優化。

### PM 必須問我
- 改變 NOW；新增路線／模型／帳號；任何付費；資料外送範圍；安全邊界放寬；刪除資料；Reviewer 配對例外。

### PM 回報格式（每週一次，不超過一頁）
```text
NOW：<項目> 進度 <%>；Owner 可驗收的東西：<有/無，怎麼驗>
本週 merged PR：<n>（其中服務 NOW 的 <n>）
成本：Codex tokens <n>、Reviewer 輪數 <n>、Mac CI 分鐘 <n>、EC2 分鐘 <n>、我手動命令 <n>
容量：ACTIVE worktree <n>、磁碟剩餘 <GB>
BLOCKED：<項目、原因、需要我的決定（是/否）>
下週 NOW：
你需要做：無 / <一個動作>
```

## 8. 什麼事情不該由 Owner 管

| 不該管 | 改成 |
|---|---|
| 額度暫停／恢復（10-19～10-27 至少 8 次） | monitor 判定；PM 在已 ALLOWED 路線內改派（OWNER_DECISION_REQUIRED：dispatch 切換規則） |
| 每個 AGY／gw 的參數（thinking、max_tokens、模型名） | PM 在預算內決定；只回報結果（AGY 的 Owner-only 指派為現行 AGENTS.md 規則，改變需 OWNER_DECISION_REQUIRED） |
| Reviewer 用哪個帳號 | PM 決定；獨立性靠 session 與 D6 紀錄（現行規則已如此） |
| 每則決策的 GitHub 代記 | 每週一則決策批次留言；日常決策不上 GitHub（OWNER_DECISION_REQUIRED：Owner 10-28 決策紀錄規則） |
| merge 順序、merge train | PM；預設直接合併已 PASS 的 PR（OWNER_DECISION_REQUIRED：合併流程） |
| 看 CI log、diff | 永遠不 |

## 9. 如何驗收 AI 開發成果

### 9.1 驗收範本

```text
驗收：<需求標題>
我做了：<步驟>
我看到：<結果>
通過條件：<原需求的驗收句>
結果：PASS / FAIL / PARTIAL
證據：<Task ID / PR / 截圖或輸出片段>
技術債：PM 回報新增了什麼（檔案數、文件頁數、新 gate）
文件：使用者文件有沒有更新（USER.md）
```

### 9.2 完成的定義（任何功能標 DONE 前）
- 我親手跑過（不是 PM 跑過）。
- 有 E2E 證據（Task 從提交到終態）。
- 符合原始需求句，而不是「相關功能已合併」。
- 沒有新增我沒同意的 gate／文件／路線。

### 9.3 不算完成
- PR merged、CI 綠、Reviewer PASS、Roadmap 標 ✅、PM 說「已可用」。（M3、M8、AUDIT-002）

## 10. 如何管理成本

- 成本 = provider tokens + Reviewer 輪數 + CI 分鐘 + PM 手動命令數 + 我的決策數。只看第一項會誤判（DEC-008、DEC-029）。
- 每個優化決策附「前／後」兩個數字；沒有數字不准標「已節省」。
- 低價模型規則：只做合成評測或離線批次；真實任務失敗兩次即不再派（#290 歷史）。
- 審查分級：docs／test-only 不用高階模型正式審（M11）。（OWNER_DECISION_REQUIRED：AGENTS.md 現行要求文件 PR 亦須正式審查）
- 預算上限：每週 Codex prompt tokens、Mac CI 分鐘各設一個數字（先量兩週基準再設）；超過即停新派工，PM 回報原因。

## 11. 如何避免需求膨脹

- 新路線／新 UI／新產品（CliNest）一律 FROZEN，直到 MVP 驗收三次。（OWNER_DECISION_REQUIRED：Roadmap）
- 每個新機制上線後看使用計數；持續 0 使用 → 檢討候選（移除為 OWNER_DECISION_REQUIRED；觀察窗由 PM 依任務週期設定）。
- 「順便」禁止：一個需求一個 PR 範圍；PM 發現相鄰問題開 Issue，不擴 PR。
- 文件上限：政策核心文件合計體積設一個上限，先刪再加（AUDIT-010；具體 KB 數待 PM 實測「一個 session 必讀 tokens」後提出，v1 的 60 KB 為審查者估計）。

## 12. 如何處理重大技術決策

1. 先問「不做會怎樣」。
2. 三選項（第 4 章）。
3. 要 PoC 時：一週內要看到真實執行，否則停。
4. 寫停損條件。
5. 兩週後回看數字；達標才擴大。

歷史對照：#172 架構原則（DEC-017）是好決策，因為逐項討論、每項有 ACCEPTED／OPEN 標記；fake-only（DEC-014）是壞決策，因為沒有停損也沒有真實呼叫期限。

## 13. 如何避免重複過去的錯誤（對照表）

| 過去模式 | 觸發訊號 | 我該說的話 |
|---|---|---|
| 先建框架後驗證 | 提案裡有「contract」「gate」「fake」「offline」而沒有日期 | 「最小版本和真實執行日期？」 |
| 額度反覆 | 「X 的 5 小時上限到了」 | 「照已允許的路線改派，不用問我。」 |
| 開新路線 | 「我們可以試試 Y 模型／CLI」 | 「主線通了嗎？沒有就凍結。」 |
| PR 當進度 | 週報只有 PR 數 | 「我能驗收什麼？」 |
| 文件膨脹 | 新增 > 2 頁規範 | 「先刪再加；一頁。」 |
| 省錢未量測 | 「可以省 token」 | 「前後數字？停損？」 |
| 修工具的工具 | 「需要一個 helper 來檢查 helper」 | 「它擋住了哪個真實事故？」 |

## 14. 實際範本與 Checklist

### 14.1 提交需求前 Checklist
- [ ] 一句話問題 + 具體情境
- [ ] 必要／想法
- [ ] 主線關係
- [ ] 驗收步驟（我會做什麼、看到什麼）
- [ ] 不要做清單
- [ ] 期限與停損

### 14.2 決策前 Checklist
- [ ] 三選項含「不做」
- [ ] 成本含 token／CI／PM／我
- [ ] 對 NOW 的影響
- [ ] PoC 日期
- [ ] 停損與量測

### 14.3 開發中 Checklist（每週）
- [ ] NOW 有 Owner 可驗收的進展
- [ ] BLOCKED 清單只含需要我的項目
- [ ] 成本與容量數字在上限內
- [ ] 沒有新路線／新文件偷跑

### 14.4 完成時 Checklist
- [ ] 我親手跑過
- [ ] E2E 證據（Task 終態）
- [ ] 符合原需求句
- [ ] 技術債與文件已回報
- [ ] 使用計數已開始記錄

### 14.5 何時停止或重新評估（數字為待驗證的起始建議，先量基準再定）
- 一段觀察期（建議兩週）沒有真實執行證據。
- 同一 root cause 第三次修復（#92 規則，現行政策）。
- 一條路線真實任務成功率明顯偏低（需兩次以上樣本；門檻待定）。
- 一個機制上線後持續 0 使用。
- NOW 連續兩週無 Owner 可驗收進展。
- 磁碟可用空間低於 PM 實測的 D6 bootstrap／CI 安全水位；Mac CI 時間高於實測基準；OPEN 核心 PR 數持續上升。（v1 的 20 GB／15 分／3 個為審查者估計）

## 15. 建議我立即實施的五項管理改變

1. **本週起每週一個 Owner 任務**，從 TUI 到 merge，結果寫進週報；失敗即下週 P0。（Owner 自身做法，無需政策變更）
2. **宣告 NOW = 一條鏈 E2E；其餘全部 FROZEN**（含 AGY、gw 真實題、OpenCode、Telegram、Web、CliNest、High Debug 自動化）。（OWNER_DECISION_REQUIRED：Roadmap 與 dispatch 切換）
3. **額度與 CLI 可用性交給 monitor 與 PM**，目標是不再因額度修改 `worker-dispatch.json`。（OWNER_DECISION_REQUIRED：dispatch 規則）
4. **對 AI 提案一律要求最小版本 + 真實執行日期 + 停損**；用第 4 章範本。（Owner 自身做法）
5. **建立一頁成本與容量看板**（Codex tokens、Reviewer 輪數、Mac／EC2 分鐘、PM 手動命令、ACTIVE worktree、磁碟），每週看一次；沒有數字的「節省」不採信。（工程建議，可由 PM 在現行授權內建立）
