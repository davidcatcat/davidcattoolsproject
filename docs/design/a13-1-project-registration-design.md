# A13.1 Project Registration, Trust, and Authorization Design

Status: Proposed design only (nothing implemented). Implementation waits for formal review of this note. Real external repository mutation requires separate Owner authorization.

Records: tracking `#2793`; Owner permission comment `7242743327`; [ROADMAP A13.1](../../tools/llmtool/ROADMAP.md); [A13.0 ProjectContext Consumer Handoff](./a13-project-context-consumer-handoff.md); [A13 trust.json design](./a13-trust-json-design-369.md).

## 1. Starting Point and Schema Conflicts to Resolve

Today `tools/llmtool/llmtool/trust.py` (`load_trust`, `verify_repository`) binds one OS user to one repository via `~/.config/llmtool/trust.json` in a single process-wide cache. `tools/llmtool/llmtool/project_context.py` (`ProjectContext.from_trust`, `ProjectContext.__init__`) defines an immutable `ProjectContext` with no production consumers yet (see [A13.0 ProjectContext Consumer Handoff](./a13-project-context-consumer-handoff.md)). `tools/llmtool/llmtool/github_identity.py` (`owner_login`, `ai_login`, `ai_gh_config_dir`, `ai_github_env`, `github_identity`) fixes two GitHub logins and `~/.config/gh-ai`, while `tools/llmtool/llmtool/review_exchange.py` (`_context`, `prepare_request`, `author_root`, `review_root`) checks fixed `AUTHOR`/`REVIEWER` session UUIDs and fixed `/codex` and canonical roots.

Routing `trust.py` (`load_trust`) through `project_context.py` (`ProjectContext.from_trust`) currently fails for every valid trust file (including migrated self-development) because of two conflicts that A13.1 must resolve:

1. **Root-overlap invariant**: `tools/llmtool/llmtool/trust.py` (`_validate_roots`, `_strict_child`, `_overlap`) requires `tasks_root` to be a strict child of `workspace_root`, whereas `tools/llmtool/llmtool/project_context.py` (`_validate_roots`, `_overlaps`) rejects any overlap among `canonical_root`, `workspace_root`, and `tasks_root` with `PROJECT_CONTEXT_INVALID`. A13.1 aligns `project_context.py` (`_validate_roots`) to the `trust.py` (`_validate_roots`) rule: `canonical_root` and `workspace_root` must not overlap, and `tasks_root` must be a strict child of `workspace_root`.
2. **Input shape**: `tools/llmtool/llmtool/project_context.py` (`ProjectContext.from_trust`, `from_trust`) accepts only a `Mapping` with exactly four keys (`canonical_root`, `workspace_root`, `tasks_root`, `repository`, with optional `approval_refs` checked in `ProjectContext.from_trust`), whereas `tools/llmtool/llmtool/trust.py` (`load_trust`, `_validate_schema`) validates seven keys and returns a `TrustConfig` dataclass. A13.1 updates `project_context.py` (`ProjectContext.from_trust`, `from_trust`) to accept a `TrustConfig` instance (or a project trust mapping including `target_branch` and GitHub identity fields) rather than rejecting seven-key trust configs. `ProjectContext` construction remains pure and side-effect-free.

## 2. Local Registry, Explicit Project Registration, and Isolated State

- **Local registry**: An owner-only registry at `<OWNER_HOME>/.config/llmtool/projects.json` indexing per-project records under `<OWNER_HOME>/.config/llmtool/projects/<project_id>.json`, read using the same `O_NOFOLLOW`, `0700` directory, `0600` regular file, `nlink == 1`, and no-`.git`-ancestor algorithm as `tools/llmtool/llmtool/trust.py` (`_read_trust_bytes`, `load_trust`, detailed in [A13 trust.json design](./a13-trust-json-design-369.md)).
- **Explicit registration**: An operator explicitly registers a project (e.g., `llmtool project register`) by validating `project_id` (`tools/llmtool/llmtool/project_context.py` `_validate_project_id`, `_printable_ascii`: 1–100 printable ASCII characters, plus filesystem-safe registry key rules), `canonical_root`, `workspace_root`, `tasks_root`, `allowed_origins`, `target_branch`, GitHub identity and permissions, and project policy before writing the registry entry.
- **Explicit selection and isolated state**: Every mutating or repository-sensitive operation requires an explicit `--project <project_id>` or an unambiguous registered working-tree match; unregistered or ambiguous targets fail closed (`PROJECT_UNREGISTERED` or `PROJECT_CONTEXT_AMBIGUOUS`). Each project stores its own trust, policy, D6 registry, tasks, logs, `GH_CONFIG_DIR`, and evidence in project-scoped directories so projects cannot collide.

## 3. Stable Repository Identity, Canonical Root, Worktree Boundary, and Target Branch

- **Stable repository identity**: Each project binds `project_id`, `repository.slug`, `repository.allowed_origins` (exact SSH/HTTPS forms), `target_branch`, `owner_login`, `ai_login`, `ai_gh_config_dir`, and `trust_binding_sha256` computed by `tools/llmtool/llmtool/trust.py` (`_binding`) and mirrored identically by `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_load_trust`).
- **Canonical root and worktree boundary**: Within each project, `canonical_root` (primary checkout, not a linked worktree) and `workspace_root` must not overlap, and `tasks_root` must be a strict child of `workspace_root` (`tools/llmtool/llmtool/trust.py` `_validate_roots`). Across projects, `canonical_root`, `workspace_root`, and `tasks_root` must not overlap any other registered project's roots.
- **Target branch**: Each project explicitly configures `target_branch` (set to `main` during explicit migration of self-development, never inferred). PR base targets, merge-base checks, and `d6_worktree_lifecycle.py` (`_publication`, `_check_merge_evidence`) use `target_branch` instead of hardcoded `origin/main`.

## 4. Project-Scoped Trust, Policy, and Mutating-Operation Verification

- **Project-scoped trust and policy**: Each project carries its own trust and validation/CI policy per [ROADMAP A13.1](../../tools/llmtool/ROADMAP.md). Self-development keeps its existing CI/runner/approval gates; external projects configure project-scoped checks and optional `approval_refs` (`tools/llmtool/llmtool/project_context.py` `_validate_approval_refs`). Target repository files remain untrusted and never grant execution, credentials, or policy overrides.
- **Verification on every mutating operation**: Because `tools/llmtool/llmtool/trust.py` (`load_trust`) intentionally performs no Git or subprocess checks, every mutating operation (D6 worktree creation/resume/record/rebind/retire/reconcile/lease-release, task dispatch/completion, exchange request preparation, and any Git or GitHub write) must call `tools/llmtool/llmtool/trust.py` (`verify_repository`)—or its hardened Git equivalent in `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_trusted_dispatcher_git`, `create_worktree`)—to verify `canonical_root` (`--show-toplevel`, `--git-common-dir`, `--absolute-git-dir`), `remote get-url origin` in `allowed_origins`, and path identity against the selected `ProjectContext` before mutating state.

## 5. GitHub Identity, Permissions, and Session Identity Guard (Design Only)

- **Project-scoped GitHub identity (`github_identity.py`)**: Replace the fixed logins in `tools/llmtool/llmtool/github_identity.py` (`owner_login`, `ai_login`, `github_identity`) with project-scoped `owner_login` and `ai_login` (`owner_login != ai_login`), and replace `~/.config/gh-ai` in `tools/llmtool/llmtool/github_identity.py` (`ai_gh_config_dir`, `ai_github_env`) with `<OWNER_HOME>/.config/llmtool/projects/<project_id>/gh` passed as `GH_CONFIG_DIR`.
  - *Required repository permissions*: On `repository.slug`, `ai_login` requires repository-scoped `push` (branch/content write), `pull_request` (create/update PRs), `issues`/comments (read/post Task/PR comments), and `checks`/`actions` read permissions; it must not hold `admin`, `maintain`, branch-protection bypass, or broad cross-repository write scopes unless explicitly authorized by the Owner. `owner_login` holds repository `admin`/owner and merge authority on `repository.slug`.
  - *Checks at registration and before mutation*: Registration and pre-mutation host checks run `gh` in the project-scoped environment from `tools/llmtool/llmtool/github_identity.py` (`ai_github_env`) to verify that the authenticated `gh api user` login matches `ai_login` (or `owner_login` for Owner-gated actions) and that `gh api repos/<repository.slug>` permissions (and inspectable token scopes) are present and not excessive.
  - *Refusals*: `owner_login == ai_login`, invalid login format, unauthenticated `gh`, or authenticated login != expected `ai_login`/`owner_login` fails with `GITHUB_IDENTITY_INVALID`. Missing `repository.slug` permissions fail with `GITHUB_PERMISSION_DENIED`. Admin/maintain/bypass or unauthorized cross-repo write scopes on `ai_login` fail with `GITHUB_PERMISSION_EXCESSIVE`.
- **Project-scoped session identity guard (`review_exchange.py`)**: Replace the fixed `AUTHOR`/`REVIEWER` session UUIDs and fixed roots in `tools/llmtool/llmtool/review_exchange.py` (`_context`, `prepare_request`, `author_root`, `review_root`) as follows:
  - *Authoritative record*: The host-owned D6 worktree registry record (`tools/llmtool/scripts/d6_worktree_lifecycle.py` `_read_registry_record`) and the project-scoped Task/dispatch record under the active `ProjectContext` are authoritative—never data supplied alongside the bundle (`expect` or `bundle`).
  - *Comparison in `_context`*: `tools/llmtool/llmtool/review_exchange.py` (`_context`) compares `dev` (`from_agent`) and `reviewer` (`to_agent`) against the active `ProjectContext` roots and the authoritative D6/task records (`session_id` == registered `session_ref`/`native_session_id`, `root` == registered `root_realpath` under the project's `tasks_root`/`workspace_root`, `agent_id` == `trusted_agent_id`, `dev.agent_id != reviewer.agent_id`, and `Role.DEVELOPER` / `Role.REVIEWER`), rejecting mismatches with `EXCHANGE_RECIPIENT_INVALID`.
  - *Replacement in `prepare_request`*: Remove the `AUTHOR` default in `tools/llmtool/llmtool/review_exchange.py` (`prepare_request`); require an explicit caller session identity (e.g., `CODEX_THREAD_ID` or explicit session argument) and verify it and `Path.cwd()` directly against the authoritative host-owned D6/task record (`EXCHANGE_RECIPIENT_INVALID` if missing or mismatched).

## 6. Explicit Migration from Self-Development (No Implicit Fallback)

- Existing self-development uses `~/.config/llmtool/trust.json`. Migration is explicit (e.g., `llmtool project register --from-legacy-trust`): it reads the legacy file, writes an explicit `project_id` entry with `target_branch` set to `main` and the existing GitHub logins and project-scoped `GH_CONFIG_DIR`, and marks the legacy file migrated.
- **No implicit fallback**: If the local registry is missing or a target is unregistered, `tools/llmtool/llmtool/trust.py` (`load_trust`) and `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_load_trust`) fail closed and never silently fall back to `~/.config/llmtool/trust.json` or hardcoded constants.
- **Existing D6 records across binding expansion**: Extending `trust_binding_sha256` in `tools/llmtool/llmtool/trust.py` (`_binding`) and `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_load_trust`) to include `project_id`, `target_branch`, `owner_login`, `ai_login`, and `ai_gh_config_dir` changes the digest for pre-A13.1 stamped self-development records. Migration does not silently restamp active records or fall back to the old 5-field digest: pre-A13.1 active worktrees are either retired before cutover, restamped via an explicit Owner/PM migration command that verifies `root_realpath`, `git_common_dir`, and the legacy 5-field digest, or released via `--release-retain` if already absent (`D6_TRUST_ROTATED`). Legacy unstamped records remain governed by `d6_worktree_lifecycle.py` (`_trust_binding_status`).

## 7. Changed Refusals and Negative Cases (A13.1 Acceptance)

- **Refusals that change**:
  - `tools/llmtool/llmtool/trust.py` (`load_trust`, `verify_repository`): Instead of a single global cache returning `TRUST_MISSING`/`TRUST_REPOSITORY_INVALID` against one repo, `load_trust` resolves an explicit `project_id` (`PROJECT_UNREGISTERED` if absent, `PROJECT_CONTEXT_AMBIGUOUS` if unresolved) and `verify_repository` validates `canonical_root` and `origin` against that project.
  - `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_load_trust`, `_trusted_dispatcher_git`, `create_worktree`, `resume_worktree`, `record_result`, `bind_native_session`, `rebind_device_tasks`, `retire_worktrees`, `_retire_plan`, `reconcile_registry`, `lease_status_report`, `_lease_registry`, `release_expired_lease`, `release_retained_records`, `_trust_binding_status`, `_require_trust_binding`, `_recheck_trust_after_lock`): All entry points resolve `trust` for the selected `project_id` and bind `D6_ORIGIN_INVALID`, `D6_REPOSITORY_INVALID`, `D6_COMMON_DIR_INVALID`, `D6_WORKSPACE_ROOT_INVALID`, `ENV_BOOTSTRAP_SOURCE_UNTRUSTED`, and `D6_TRUST_ROTATED` to that project's registry entry and extended `trust_binding_sha256` (including `rebind_device_tasks`, `retire_worktrees`, and `reconcile_registry`, which previously bound to the single global `trust.json`). `_publication` and `_check_merge_evidence` check `origin/<project.target_branch>` instead of `origin/main`.
  - `tools/llmtool/llmtool/review_origins.py` (`review_trust`, `trusted_repository`, `trusted_slug`, `origin_allowed`, `host_policy_reference_pattern`, `actions_run_pattern`): Used by review authority and collector code; `review_trust` resolves the active `project_id` (failing closed with `PROJECT_UNREGISTERED`/`PROJECT_CONTEXT_AMBIGUOUS`) so origin and slug checks bind to the selected project rather than a single global `trust.json`.
  - `tools/llmtool/llmtool/review_exchange.py` (`_context`, `prepare_request`, `wait_report`, `author_root`, `review_root`): `trusted_slug()` and `review_trust()` bind to the active `project_id` (`EXCHANGE_BINDING_INVALID` on repository slug mismatch; `PROJECT_UNREGISTERED`/`PROJECT_CONTEXT_MISMATCH` on missing or mismatched project context).
- **Required negative cases**:
  1. Unregistered target (`PROJECT_UNREGISTERED`); no implicit fallback to legacy `trust.json`.
  2. Ambiguous context (`PROJECT_CONTEXT_AMBIGUOUS`).
  3. Wrong origin (`TRUST_REPOSITORY_INVALID` / `D6_ORIGIN_INVALID` / review origin rejection).
  4. Wrong root, worktree boundary, or repository identity other than origin: linked worktree as `canonical_root`, cross-project root overlap, `repository.slug` / `local_facts.repository` mismatch, `git_common_dir` mismatch, or `target_branch` mismatch (`TRUST_REPOSITORY_INVALID` / `TRUST_PATHS_OVERLAP` / `D6_REPOSITORY_INVALID` / `D6_COMMON_DIR_INVALID` / `EXCHANGE_BINDING_INVALID`).
  5. Wrong identity: authenticated `gh` login in project `GH_CONFIG_DIR` differing from registered `ai_login` or `owner_login`, `owner_login == ai_login`, missing or excessive `repository.slug` permissions (`GITHUB_IDENTITY_INVALID`, `GITHUB_PERMISSION_DENIED`, `GITHUB_PERMISSION_EXCESSIVE`), or mismatched exchange session/authoritative D6 record (`EXCHANGE_RECIPIENT_INVALID`).
  6. Stale identity: rotated `trust_binding_sha256` (including post-creation `owner_login`, `ai_login`, `ai_gh_config_dir`, `project_id`, or `target_branch` change) or mid-run change (`D6_TRUST_ROTATED`, `TRUST_CHANGED_DURING_RUN`).
  7. Cross-project access: task, worktree, `GH_CONFIG_DIR`, or evidence from another project (`PROJECT_CONTEXT_MISMATCH` / `PROJECT_CONTEXT_INVALID`).
