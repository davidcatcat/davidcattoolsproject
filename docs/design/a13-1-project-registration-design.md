# A13.1 Project Registration, Trust, and Authorization Design

Status: Proposed design only (nothing implemented). Implementation waits for formal review of this note. Real external repository mutation requires separate Owner authorization.

Records: tracking `#2793`; Owner permission comment `7242743327`; [ROADMAP A13.1](../../tools/llmtool/ROADMAP.md); [A13.0 ProjectContext Consumer Handoff](./a13-project-context-consumer-handoff.md); [A13 trust.json design](./a13-trust-json-design-369.md).

## 1. Starting Point and Schema Conflicts to Resolve

Today `tools/llmtool/llmtool/trust.py` (`load_trust`, `verify_repository`) binds one OS user to one repository via `~/.config/llmtool/trust.json` in a single process-wide cache. `tools/llmtool/llmtool/project_context.py` (`ProjectContext.from_trust`, `ProjectContext.__init__`) defines an immutable `ProjectContext` with no production consumers yet (see [A13.0 ProjectContext Consumer Handoff](./a13-project-context-consumer-handoff.md)). `tools/llmtool/llmtool/github_identity.py` (`owner_login`, `ai_login`, `ai_gh_config_dir`, `ai_github_env`, `github_identity`) fixes two GitHub logins and `~/.config/gh-ai`, while `tools/llmtool/llmtool/review_exchange.py` (`_context`, `prepare_request`, `author_root`, `review_root`) checks fixed `AUTHOR`/`REVIEWER` session UUIDs and fixed `/codex` and canonical roots.

Routing `tools/llmtool/llmtool/trust.py` (`load_trust`) through `tools/llmtool/llmtool/project_context.py` (`ProjectContext.from_trust`) currently fails for every valid trust file because of two conflicts that A13.1 resolves:

1. **Root-overlap invariant**: `tools/llmtool/llmtool/project_context.py` (`_validate_roots`, `_overlaps`) rejects any overlap among `canonical_root`, `workspace_root`, and `tasks_root` with `PROJECT_CONTEXT_INVALID`, whereas `tools/llmtool/llmtool/trust.py` (`_validate_roots`, `_strict_child`, `_overlap`) requires `tasks_root` to be a strict child of `workspace_root`. A13.1 aligns `project_context.py` (`_validate_roots`) to the `trust.py` rule defined in §5.
2. **Input shape**: `tools/llmtool/llmtool/project_context.py` (`ProjectContext.from_trust`, `from_trust`) accepts only a `Mapping` with four keys (`canonical_root`, `workspace_root`, `tasks_root`, `repository`, with optional `approval_refs` checked in `ProjectContext.from_trust`), whereas `tools/llmtool/llmtool/trust.py` (`load_trust`, `_validate_schema`) validates seven keys (`schema_version`, `canonical_root`, `workspace_root`, `tasks_root`, `repository`, `ci_trust`, `tools`) and returns a `TrustConfig` dataclass. A13.1 updates `project_context.py` (`ProjectContext.from_trust`, `from_trust`) to accept a `TrustConfig` instance (or a project trust mapping including `target_branch` and GitHub identity fields) while keeping `ProjectContext` construction pure and side-effect-free.

## 2. Local Registry and Isolated State

- **Local registry**: An owner-only registry at `<OWNER_HOME>/.config/llmtool/projects.json` (proposed) indexes per-project trust records at `<OWNER_HOME>/.config/llmtool/projects/<project_id>.json` (proposed). Both are read using the `O_NOFOLLOW`, `0700` directory, `0600` regular file, `nlink == 1`, and no-`.git`-ancestor algorithm in `tools/llmtool/llmtool/trust.py` (`_read_trust_bytes`, `load_trust`), detailed in [A13 trust.json design](./a13-trust-json-design-369.md).
- **`project_id` key syntax and collision rejection**: `tools/llmtool/llmtool/project_context.py` (`_validate_project_id`, `_printable_ascii`) currently accepts any 1–100 printable ASCII characters, including `/`, `\`, `..`, and mixed case. Because per-project records and state are stored under `project_id`, A13.1 restricts `project_id` (proposed) to lowercase ASCII slugs matching `^[a-z0-9][a-z0-9._-]{0,63}\Z` with no `/`, `\`, `..`, whitespace, or leading `.`, validated before any path is derived. Invalid keys fail closed with `PROJECT_CONTEXT_INVALID` in `ProjectContext` or `PROJECT_ID_INVALID` (proposed) at registry/CLI boundaries. Registration checks for colliding keys (including case-folded matches against existing `projects.json` entries and `projects/` filenames) and refuses duplicates with `PROJECT_ALREADY_EXISTS` (proposed).
- **Isolated state**: Each registered project stores its own trust, policy, D6 registry, tasks, logs, `GH_CONFIG_DIR` (`<OWNER_HOME>/.config/llmtool/projects/<project_id>/gh`, proposed), and evidence in project-scoped directories so projects cannot collide or leak state.

## 3. Explicit Project Registration and Selection

- **Explicit registration**: An operator explicitly registers a project (e.g., `llmtool project register`, proposed) by validating `project_id`, `canonical_root`, `workspace_root`, `tasks_root`, `allowed_origins`, `target_branch`, GitHub identity and permissions, and project policy before writing the registry entry.
- **Explicit selection**: Every mutating or repository-sensitive operation requires an explicit `--project <project_id>` (proposed) or an unambiguous registered working-tree match. Unregistered targets fail closed with `PROJECT_UNREGISTERED` (proposed); ambiguous working-tree matches fail closed with `PROJECT_CONTEXT_AMBIGUOUS` (proposed).

## 4. Stable Repository Identity

Each project binds `project_id`, `repository.slug`, `repository.allowed_origins` (exact SSH/HTTPS forms), `target_branch`, `owner_login`, `ai_login`, `ai_gh_config_dir`, and `trust_binding_sha256` computed by `tools/llmtool/llmtool/trust.py` (`_binding`) and mirrored identically by `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_load_trust`).

## 5. Canonical Root and Worktree Boundary

Within each project, `canonical_root` (the primary checkout, not a linked worktree) and `workspace_root` must not overlap, and `tasks_root` must be a strict child of `workspace_root` (`tools/llmtool/llmtool/trust.py` `_validate_roots`, `_strict_child`, `_overlap`). Across registered projects, `canonical_root`, `workspace_root`, and `tasks_root` must not overlap any other project's roots (`TRUST_PATHS_OVERLAP`).

## 6. Target Branch

Each project explicitly configures `target_branch` (never inferred). PR base targets, merge-base checks, `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_publication`, `_check_merge_evidence`), and `tools/llmtool/llmtool/task_completion.py` (`collect_github_evidence`) use the selected project's `target_branch` instead of hardcoded `origin/main` or `'main'`.

## 7. Project-Scoped Trust and Policy

Each project carries its own trust and validation/CI policy per [ROADMAP A13.1](../../tools/llmtool/ROADMAP.md). Self-development keeps its existing CI, runner, and approval gates; external projects configure project-scoped checks and optional `approval_refs` (`tools/llmtool/llmtool/project_context.py` `_validate_approval_refs`). Target repository files remain untrusted and never grant execution, credentials, or policy overrides.

## 8. Mutating-Operation Repository and Path Validation

- **Separation of tooling trust from target project trust**: `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_trusted_dispatcher_git`, `_approved_task_source`, `_run_approved_lifecycle`, `_bootstrap`) and `tools/llmtool/scripts/d6_worktree_env.py` (`_validate_bootstrap_sources`) verify `llmtool`'s own dispatcher/helper source files and refuse with `ENV_BOOTSTRAP_SOURCE_UNTRUSTED` or `D6_BOOTSTRAP_SOURCE_MISMATCH`. That tooling-source check must be separated from target project trust: `ENV_BOOTSTRAP_SOURCE_UNTRUSTED` binds to `llmtool`'s own installation/source trust, never to an external project's `canonical_root` or `allowed_origins`, so external repositories (which do not contain `tools/llmtool/`) are not refused as untrusted `llmtool` sources.
- **Target repository verification before every mutation**: Because `tools/llmtool/llmtool/trust.py` (`load_trust`) performs no Git or subprocess checks, every mutating operation (D6 worktree creation, resume, result recording, native-session binding, device rebind, retirement, reconciliation, lease release, task dispatch/completion, exchange request preparation, and any Git or GitHub write) must call `tools/llmtool/llmtool/trust.py` (`verify_repository`)—or its hardened Git equivalent in `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`create_worktree`, `rebind_device_tasks`, `retire_worktrees`) and `tools/llmtool/scripts/d6_worktree_env.py` (`validate_registered_worktree`)—to verify `canonical_root` (`--show-toplevel`, `--git-common-dir`, `--absolute-git-dir`), `remote get-url origin` in `allowed_origins`, and path identity against the selected `ProjectContext` before mutating state.
- **D6 environment script (`d6_worktree_env.py`)**: `tools/llmtool/scripts/d6_worktree_env.py` (`_load_trust`, `validate_registered_worktree`, `main`) currently embeds `# BEGIN llmtool-trust-reader v1` to read only the legacy `trust.json`, checks `origin not in trust["origins"]` (`D6_SOURCE_BINDING_MISMATCH`), and compares `--trust-sha256` against `trust["sha256"]` (`TRUST_CHANGED_DURING_RUN`). In A13.1, `d6_worktree_env.py` (`_load_trust`, `main`) is updated to resolve the selected project's trust record (matching `d6_worktree_lifecycle.py` and `trust.py`) and verify `--trust-sha256` against that project's trust digest.

## 9. GitHub Identity and Permissions

- **Project-scoped GitHub identity (`github_identity.py`)**: Replace the fixed logins and `~/.config/gh-ai` in `tools/llmtool/llmtool/github_identity.py` (`owner_login`, `ai_login`, `ai_gh_config_dir`, `ai_github_env`, `github_identity`) with project-scoped `owner_login` and `ai_login` (`owner_login != ai_login`) and `<OWNER_HOME>/.config/llmtool/projects/<project_id>/gh` passed as `GH_CONFIG_DIR`.
- **Separate Owner vs AI contexts**: `ai_github_env` (`github_identity.py`) and `verified_ai_env` (`tools/llmtool/llmtool/ai_github_exec.py`) remain strictly **AI-only**: `verified_ai_env` accepts only `ai_login` inside the project's `ai_gh_config_dir` and never accepts `owner_login`. Any Owner identity or Owner permission check runs in a **separate Owner `gh` context** (the Owner's own `gh` configuration, isolated from `ai_gh_config_dir`).
- **Verifiable permission probes and fail-closed limits**:
  - *AI authenticated login*: `gh api -i user` in `ai_github_env` verifies `.login == ai_login` (`AI_GH_LOGIN_MISMATCH` in `ai_github_exec.py` `verified_ai_env`; `REVIEWER_GITHUB_LOGIN_MISMATCH` in `tools/llmtool/llmtool/review_dispatch.py` `_resolve_github_login`; missing dir fails with `AI_GH_CONFIG_MISSING`).
  - *Owner authenticated login*: `gh api user --jq .login` in the separate Owner `gh` context verifies `.login == owner_login` (`GITHUB_IDENTITY_INVALID`, proposed).
  - *Repository role flags (AI and Owner)*: `gh api repos/<repository.slug>` in the AI context verifies `permissions.push == true` and `permissions.admin == false` and `permissions.maintain == false` (missing `push` fails with `GITHUB_PERMISSION_DENIED` [proposed]; `admin` or `maintain` true fails with `GITHUB_PERMISSION_EXCESSIVE` [proposed]). In the separate Owner context, `gh api repos/<repository.slug>` verifies `permissions.admin == true` (missing `admin` fails with `GITHUB_PERMISSION_DENIED` [proposed]).
  - *Read probes for PRs, issues, checks, and Actions*: `gh api repos/<repository.slug>/pulls?per_page=1`, `issues?per_page=1`, `actions/runs?per_page=1`, and `commits/<target_branch>/check-runs` in the AI context verify read access (403/404 fails with `GITHUB_PERMISSION_DENIED`, proposed).
  - *Branch-protection bypass*: `gh api repos/<repository.slug>/branches/<target_branch>/protection` or `rules/branches/<target_branch>` (in Owner context if unreadable by AI) checks that `ai_login` is not a bypass actor (`GITHUB_PERMISSION_EXCESSIVE`, proposed).
  - *Token scopes and cross-repository write access (fail-closed)*: `gh api repos/<repository.slug>` reports only coarse role flags, not fine-grained PAT permissions (`pull_requests`, `issues`, `checks`, `actions` write vs read) or cross-repository write access. Where `X-OAuth-Scopes` is present on `gh api -i user`, unauthorized broad scopes (e.g., `repo`, `admin:org`, `delete_repo`, `workflow` without explicit Owner authorization) fail with `GITHUB_PERMISSION_EXCESSIVE` (proposed). When `X-OAuth-Scopes` is absent (fine-grained PAT) or token permissions/cross-repo scopes cannot be inspected via GitHub's API, the check **fails closed** (`GITHUB_PERMISSION_UNVERIFIED`, proposed) rather than passing; the exact fine-grained PAT inspection mechanism remains **open** (§13).
- **Relationship to `GITHUB_IDENTITY_INVALID`**: `GITHUB_IDENTITY_INVALID` (`github_identity.py` `github_identity`) is the static/config refusal for invalid login syntax or `owner_login == ai_login` (and proposed for Owner login mismatch). `AI_GH_CONFIG_MISSING`, `AI_GH_LOGIN_MISMATCH` (`ai_github_exec.py` `verified_ai_env`), and `REVIEWER_GITHUB_LOGIN_MISMATCH` (`review_dispatch.py` `_resolve_github_login`) remain the runtime AI `gh` environment/login refusals.

## 10. Session Identity Guard

Replace the fixed `AUTHOR`/`REVIEWER` session UUIDs and fixed roots in `tools/llmtool/llmtool/review_exchange.py` (`_context`, `prepare_request`, `author_root`, `review_root`) as follows:

- **Declared root change**: `review_exchange.py` (`author_root`, `review_root`) currently returns `workspace_root + '/codex'` and `canonical_root`. A13.1 changes both to resolve the registered D6 worktree `root_realpath` under the selected project's `tasks_root` from the authoritative D6 record.
- **Authoritative records and fields**: The host-owned D6 worktree registry record at `<git_common_dir>/llmtool-worktrees/<task_id>.json` (`tools/llmtool/scripts/d6_worktree_lifecycle.py` `_read_registry_record`, `tools/llmtool/llmtool/task_completion_part2.py` `read_d6_registration`) and the project-scoped Task record (`tools/llmtool/llmtool/task_store.py` `TaskStore.get`) are authoritative—never data supplied alongside the bundle (`expect` or `bundle`). D6 record fields used are `task_id`, `trusted_agent_id`, `session_ref`, `native_session_id`, `root_realpath`, `git_common_dir`, `branch`, `state`, and `lock_state`.
- **No `role` field on existing D6 records**: Existing D6 records created by `d6_worktree_lifecycle.py` (`create_worktree`) hold no `role` field. Either `create_worktree` / `read_d6_registration` is extended to record an explicit `role` (`DEVELOPER` / `REVIEWER`), or `review_exchange.py` (`_context`) resolves role from the Task record (`developer` vs `review_dispatch_claim[].reviewer_task`) and `AgentBinding.role` (`tools/llmtool/llmtool/task_lifecycle.py` `Role`) verified against `trusted_agent_id` (this choice is marked open in §13).
- **Comparison in `_context` and `prepare_request`**: `review_exchange.py` (`_context`) verifies `dev` (`from_agent`) and `reviewer` (`to_agent`) against the active `ProjectContext` roots and authoritative D6/Task records (`session_id` == `session_ref`/`native_session_id`, `root` == `root_realpath` under `tasks_root`, `agent_id` == `trusted_agent_id`, `dev.agent_id != reviewer.agent_id`). `prepare_request` removes the `AUTHOR` default, requires an explicit caller session identity (`CODEX_THREAD_ID` or explicit argument), and verifies it and `Path.cwd()` against the authoritative D6/Task record (`EXCHANGE_RECIPIENT_INVALID` on any mismatch).

## 11. Explicit Migration from Self-Development

- **Explicit migration**: Existing self-development uses `~/.config/llmtool/trust.json`. Migration is explicit (e.g., `llmtool project register --from-legacy-trust`, proposed): it reads the legacy file, writes an explicit `project_id` entry with `target_branch` set to `main` and the existing GitHub logins and project-scoped `ai_gh_config_dir`.
- **Legacy migration marker location**: Because `tools/llmtool/llmtool/trust.py` (`_validate_schema`) requires `trust.json` to have **exact** seven keys, the migration marker **cannot** be added inside `~/.config/llmtool/trust.json`. Instead, it lives outside `trust.json` as an owner-only marker file `<OWNER_HOME>/.config/llmtool/trust.migrated` (proposed) or as `migrated_from_legacy_trust_sha256` inside `projects.json` (proposed), leaving `trust.json` unmodified.
- **Credential authentication for migrated `GH_CONFIG_DIR`**: Moving self-development to `<OWNER_HOME>/.config/llmtool/projects/<project_id>/gh` does not automatically copy credentials from `~/.config/gh-ai`, because copying credentials requires explicit Owner authorization. Either the Owner authenticates the project-scoped directory directly (`gh auth login`), or any credential-copy step requires explicit Owner authorization (marked open in §13).
- **No implicit fallback**: If `projects.json` is missing or a target is unregistered, `trust.py` (`load_trust`), `d6_worktree_lifecycle.py` (`_load_trust`), and `d6_worktree_env.py` (`_load_trust`) fail closed and never fall back to `~/.config/llmtool/trust.json` or hardcoded constants.
- **Existing D6 records across binding expansion**: Extending `trust_binding_sha256` in `trust.py` (`_binding`) and `d6_worktree_lifecycle.py` (`_load_trust`) to include `project_id`, `target_branch`, `owner_login`, `ai_login`, and `ai_gh_config_dir` invalidates pre-A13.1 stamped records (`D6_TRUST_ROTATED`). Migration does not silently restamp active records or fall back to the 5-field digest: pre-A13.1 active worktrees are either retired before cutover, restamped via an explicit Owner/PM command verifying `root_realpath`, `git_common_dir`, and the legacy 5-field digest, or released via `--release-retain` if absent. Legacy unstamped records remain governed by `d6_worktree_lifecycle.py` (`_trust_binding_status`).

## 12. Changed and Unchanged Refusals and Negative Cases

- **Refusals declared changed in target or behavior**:
  - `tools/llmtool/llmtool/trust.py` (`load_trust`, `verify_repository`): `load_trust` resolves an explicit `project_id` (`PROJECT_UNREGISTERED`, `PROJECT_CONTEXT_AMBIGUOUS`, `PROJECT_ID_INVALID` [proposed]) instead of one global `TRUST_MISSING` cache; `verify_repository` validates `canonical_root` and `origin` against the selected project (`TRUST_REPOSITORY_INVALID`).
  - `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_load_trust`, `create_worktree`, `resume_worktree`, `record_result`, `bind_native_session`, `rebind_device_tasks`, `retire_worktrees`, `_retire_plan`, `reconcile_registry`, `lease_status_report`, `_lease_registry`, `release_expired_lease`, `release_retained_records`, `_trust_binding_status`, `_require_trust_binding`, `_recheck_trust_after_lock`): All entry points resolve trust for the selected `project_id` and bind `D6_ORIGIN_INVALID`, `D6_REPOSITORY_INVALID`, `D6_COMMON_DIR_INVALID`, `D6_WORKSPACE_ROOT_INVALID`, and `D6_TRUST_ROTATED` to that project's registry entry and extended `trust_binding_sha256`. `_publication` and `_check_merge_evidence` check `origin/<project.target_branch>`.
  - `tools/llmtool/scripts/d6_worktree_lifecycle.py` (`_trusted_dispatcher_git`): `ENV_BOOTSTRAP_SOURCE_UNTRUSTED` is **unchanged in meaning for `llmtool` itself**, but separated from target project trust so it never rejects external repositories.
  - `tools/llmtool/scripts/d6_worktree_env.py` (`_load_trust`, `validate_registered_worktree`, `main`): `D6_SOURCE_BINDING_MISMATCH` (foreign origin) and `TRUST_CHANGED_DURING_RUN` (`--trust-sha256` mismatch) are **changed in target** to validate against the selected project's trust entry instead of the single legacy `trust.json`.
  - `tools/llmtool/llmtool/ai_github_exec.py` (`verified_ai_env`) and `tools/llmtool/llmtool/review_dispatch.py` (`_resolve_github_login`, `_gh_env`): `AI_GH_CONFIG_MISSING`, `AI_GH_LOGIN_MISMATCH`, and `REVIEWER_GITHUB_LOGIN_MISMATCH` are **changed in target** to check the selected project's `ai_gh_config_dir` and `ai_login`.
  - `tools/llmtool/llmtool/github_identity.py` (`github_identity`): `GITHUB_IDENTITY_INVALID` validates project-scoped `owner_login` and `ai_login` (plus proposed Owner `gh` login mismatch). Proposed new permission refusals: `GITHUB_PERMISSION_DENIED`, `GITHUB_PERMISSION_EXCESSIVE`, `GITHUB_PERMISSION_UNVERIFIED`.
  - `tools/llmtool/llmtool/review_origins.py` (`review_trust`, `trusted_repository`, `trusted_slug`, `origin_allowed`, `host_policy_reference_pattern`, `actions_run_pattern`): `review_trust` resolves the active `project_id` (`PROJECT_UNREGISTERED`, `PROJECT_CONTEXT_AMBIGUOUS`, proposed).
  - `tools/llmtool/llmtool/task_review_collector.py` (`collect_local_facts`): `REVIEW_REPOSITORY_INVALID` is **changed in target** (validates `origin` against the selected project's `allowed_origins` via `review_origins.origin_allowed`).
  - `tools/llmtool/llmtool/review_authority.py` (`RegisteredAgent.__post_init__`, `_decode_host`, `load_host_registration`): `REVIEW_REGISTRATION_INVALID` is **changed in target** for `origin_allowed(self.origin)` (selected project's `allowed_origins`); `device`/`inode`/`venv_prefix`/uniqueness checks remain **unchanged**.
  - `tools/llmtool/llmtool/review_exchange.py` (`_context`, `prepare_request`, `author_root`, `review_root`): `EXCHANGE_BINDING_INVALID`, `EXCHANGE_RECIPIENT_INVALID`, and `author_root`/`review_root` bind to the selected project's `slug`, `tasks_root`, and authoritative D6/Task records.
- **Required negative cases**:
  1. Unregistered target (`PROJECT_UNREGISTERED`, proposed) with no implicit fallback to `trust.json`.
  2. Ambiguous context (`PROJECT_CONTEXT_AMBIGUOUS`, proposed) and invalid/colliding `project_id` (`PROJECT_CONTEXT_INVALID` / `PROJECT_ID_INVALID` / `PROJECT_ALREADY_EXISTS`, proposed).
  3. Wrong origin (`TRUST_REPOSITORY_INVALID`, `D6_ORIGIN_INVALID`, `D6_SOURCE_BINDING_MISMATCH`, `REVIEW_REPOSITORY_INVALID`, `REVIEW_REGISTRATION_INVALID`).
  4. Wrong root, worktree boundary, or repository identity other than origin: linked worktree as `canonical_root`, cross-project root overlap, `repository.slug` / `local_facts.repository` mismatch, `git_common_dir` mismatch, or `target_branch` mismatch (`TRUST_REPOSITORY_INVALID`, `TRUST_PATHS_OVERLAP`, `D6_REPOSITORY_INVALID`, `D6_COMMON_DIR_INVALID`, `EXCHANGE_BINDING_INVALID`).
  5. Wrong or unverified GitHub/session identity: missing project `GH_CONFIG_DIR` (`AI_GH_CONFIG_MISSING`), AI login mismatch (`AI_GH_LOGIN_MISMATCH`, `REVIEWER_GITHUB_LOGIN_MISMATCH`), Owner login in AI `GH_CONFIG_DIR` or invalid/equal logins (`GITHUB_IDENTITY_INVALID`), missing/excessive/uninspectable permissions (`GITHUB_PERMISSION_DENIED`, `GITHUB_PERMISSION_EXCESSIVE`, `GITHUB_PERMISSION_UNVERIFIED`, proposed), or mismatched exchange session/D6 record (`EXCHANGE_RECIPIENT_INVALID`).
  6. Stale identity: rotated `trust_binding_sha256` or mid-run trust change (`D6_TRUST_ROTATED`, `TRUST_CHANGED_DURING_RUN`).
  7. Cross-project access: task, worktree, `GH_CONFIG_DIR`, or evidence from another project (`PROJECT_CONTEXT_MISMATCH`, proposed / `PROJECT_CONTEXT_INVALID`).

## 13. Open Questions and Gates

- **Open**: Exact CLI subcommand and flag names for project registration, selection, and migration (e.g., `llmtool project register` vs `llmtool trust init` integration).
- **Open**: Exact `gh` API probe or Owner-attested mechanism for fine-grained PAT scope inspection (`pull_requests`, `issues`, `checks`, `actions`, cross-repository write access) when `X-OAuth-Scopes` is absent; until defined, uninspectable scopes fail closed (`GITHUB_PERMISSION_UNVERIFIED`, proposed).
- **Open**: Whether self-development migration requires fresh `gh auth login` in the project-scoped `GH_CONFIG_DIR` or offers a credential copy step with explicit Owner authorization.
- **Open**: Whether D6 registry records gain an explicit `role` field in `d6_worktree_lifecycle.py` (`create_worktree`) or `review_exchange.py` (`_context`) derives role from `task_store.py` (`TaskStore.get`) and `trusted_agent_id`.
- **Open**: Whether pre-A13.1 active self-development D6 worktrees should be retired before migration cutover or restamped via an explicit Owner/PM migration command.
- **Gates**: Exact-head check (docs); formal review by a reviewer of another model family before any A13.1 implementation begins.
