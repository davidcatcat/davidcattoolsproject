## F3 decision and evidence

The unresolved requirement is the verification-to-group-signal race during
parent fallback after supervisor loss. B5 section 11.1 requires original-group
continuity through signaling, explicitly states that a start-time snapshot is
not an atomic handle, and requires NOT SUPPORTED when continuity cannot be
established. Section 11.2 requires killing/reaping the owned supervisor before
the parent's group fallback. The targeted re-review's F3 and the current task
require implementing this rule and adversarially testing it within this slice.

A snapshot-only implementation has this counterexample ordering:

1. The supervisor is dead/reaped; the host parent is not the fake leader's
   reaping parent.
2. A kernel snapshot matches the original leader or witnessed member's
   PID/start-time/UID/PGID/SID.
3. That last original member exits and its reaping parent releases its identity
   and group. A different process group can subsequently acquire the numeric ID.
4. The host calls `killpg` with that numeric ID, without any kernel operation
   binding this signal to the previously verified identity.

Checking twice only moves the last check; it does not bind the subsequent signal.
Retaining a kqueue exit notification is not, by itself, a demonstrated group
signaling handle. The supervisor's owned, unreaped leader can pin the group for
its own cleanup decision; that ownership argument does not transfer to the host
parent after supervisor death. This is design reasoning, not a newly executed
OS reproducer or a claim that every possible macOS approach is impossible.

Apple's published `kill`/`killpg1` source resolves an explicit group using the
numeric PGID at signal time. Its audit-token signaling path validates a target
process identity and signals that process; it is not an identity-bound group
operation. These source observations support the distinction above, but do not
prove the installed kernel's behavior or supply native acceptance evidence.
Sources: [Apple group-signal implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c),
[Apple audit-token signal implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/proc_info.c).

Read-only inspection of the installed SDK found `proc_bsdinfo` start-time fields
in `sys/proc_info.h` and the `proc_signal_with_audittoken` declaration in
`libproc.h`. Runtime symbol lookup under the venv interpreter found both
`proc_pidinfo` and `proc_signal_with_audittoken`. No process-information query or
signal was performed through those APIs. Symbol presence does not establish
identity/continuity safety, successful permission checks or OS race proof.
