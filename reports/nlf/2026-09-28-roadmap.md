## Product Principles

以下是**不可協商的產品契約**。任何 roadmap 項目如果需要違反其中一條，就不做，或先回來修改這份契約並經過人工同意。

1. **Deterministic：** 同樣的輸入、同樣的 `now`、同樣的檔案系統狀態，得到同樣的解析結果與同樣順序的輸出。
2. **Read-only：** 不修改、建立、刪除、移動、改權限或改時間戳記任何檔案。由 `TestProductionCodeIsReadOnly` 以原始碼檢查維持。
3. **執行時不使用 LLM、不連網路。**
4. **Production 搜尋不執行 shell 或任何外部程式**（不 import `os/exec`）。
5. **不自動使用 sudo**，也不嘗試任何提權。
6. **Go-native traversal：** 走訪與比對都由 Go 完成，不依賴 `find`、`grep`、`stat`。
7. **單一靜態 binary**（`CGO_ENABLED=0`），目標機器不需要 Go 或任何函式庫。
8. **macOS 與 Linux 都是一等平台**；兩邊的語意必須相同，差異只能出現在明確標示的 OS 提示與近似指令。
9. **Stdlib-first：** 預設不加第三方依賴；需要時必須先有書面理由。
10. **stdout 只放結果、可以 pipe；診斷訊息一律寫 stderr。**
11. **看不懂或有歧義 → 明確報錯（exit 2）**，附上提示。
12. **不默默擴大搜尋範圍，也不自動修正語法**（不猜、不丟掉看不懂的字、不自動對調區間）。
13. **`--explain` 永遠不搜尋。**
14. **`--confirm` 只在一整行剛好是 `y` 或 `Y` 時才執行**；其他任何輸入（含 EOF）都取消並 exit 0。
15. **近似的 shell 指令只供參考**；nlf 不執行它，實際行為以 nlf 為準。
16. **Exit code 穩定：** `0` 有結果（或 `--confirm` 取消）、`1` 查詢有效但沒有結果、`2` 錯誤。新增的 flag 不得改變這三個值的意義。

衍生的工程原則：

- 新功能預設**關閉**；任何會改變既有查詢結果的變更都要在報告的 Backward Compatibility 裡逐條列出。
- 每個 milestone 必須能獨立 review、獨立 revert，並附 regression test。
- 常見排除目錄（`.git`、`node_modules` …）**絕不能默默成為預設**，只能由使用者明確要求，而且要出現在 `--explain`。

## Current Capabilities

以下都是 0.4.0 的實際能力（依程式碼與報告，部分實測）。

**查詢條件（彼此 AND）**

| 類別 | 能力 | 備註 |
|---|---|---|
| 副檔名 | `.go`、`*.md`、`go files`、`找 ovpn 檔`、內建別名（`圖片`、`images`…）、多個副檔名本來就是 any-of | 不分大小寫；副檔名最長 10 字元、最多兩段（`tar.gz`） |
| 檔名 | exact / contains / prefix / suffix / glob（`path.Match`） | 只比對 base name；**區分大小寫**；必須寫出「檔名 / name」主詞 |
| 內容 | 逐字子字串，AND 與 OR；`ignore case` | 每個檔案只讀一次；64 KB chunk 串流，跨 chunk 保留 tail；前 64 KB 有 NUL 視為 binary 略過 |
| 修改時間（相對） | `last 7 days`、`最近 6 小時`、`3 天前`、`older than 30 days` | 月 = 30 天、年 = 365 天 |
| 修改時間（日曆） | 年、月、日、日期區間、時間區間、到現在、since、今天 / 昨天 / 本月 / 去年… | 本機時區、半開區間、DST 用日曆計算、嚴格驗證 |
| 絕對日期比較（0.4.0） | `before` / `on or before` / `after` / `on or after`、`以前 / 或以前 / 以後 / 或以後` | 只接受日、月、年；不接受時刻 |
| 大小 | `> 10MB`、`at least 1GB`、`小於 1KB`；`smaller than 1 byte` 可找空檔案（實測） | 二進位單位 |
| Boolean OR | 同類條件（副檔名、檔名、內容、時間、大小），單層，只綁定相鄰條件 | 不同類 OR 明確報錯 |
| 排除目錄 | 名稱（不分大小寫）或相對路徑（依檔案系統判斷大小寫） | 路徑在搜尋位置之外、或等於搜尋位置本身都報錯 |
| 排序 / 數量 | largest、newest、top N | 同分時依路徑排序 |
| 搜尋位置 | `--dir`、`in …`、`在 …`；兩者同時用會報錯 | 搜尋位置本身是 symlink 時跟隨 |

**CLI**

- Flags：`--explain`、`--confirm`、`-l/--long`、`-d/--dir`（含 `--dir=`）、`-h/--help`、`--version`、`--`。未知 flag 一律 exit 2（實測 `-0`、`--null`、`--json`、`--count`、`--max-depth` 都是 `unknown flag`）。
- Flag 可以放在查詢之前或之後（實測 `nlf "log files" -l` 可用）。
- `--explain` 顯示解析結果與依 OS 產生的近似 `find` 指令（macOS / GNU）；`--confirm` 在 stderr 顯示執行計畫與 Safety 摘要，只接受 `y` / `Y`。
- 訊息語言跟著查詢語言（有中文字就用中文）。
- `-l` 輸出：`大小  YYYY-MM-DD HH:MM  路徑`（沒有秒、沒有時區）。
- 未排序時依名稱順序（`filepath.WalkDir` 的 lexical 順序）輸出，達到上限就 `SkipAll` 提早停止。

**走訪與安全**

- 只回傳 regular file；目錄、symlink、FIFO、device、socket 都不會出現在結果（實測 FIFO 與指向 regular file 的 symlink 都沒有列出，也沒有被開啟）。
- 不跟隨樹內的 symlink；隱藏檔與 `.git` 會被搜尋。
- 權限不足的目錄略過並在 stderr 列出前 5 筆，附 OS 相依提示；搜尋位置本身無法讀取時 exit 2。
- 比對順序由便宜到昂貴：副檔名與檔名（不 Stat）→ `d.Info()`（大小、mtime）→ 內容（開檔）。

**工程**

- `make build / test / vet / fmt-check / check / dist`；`make dist` 產生 4 個平台的靜態 binary 與 `SHA256SUMS`。
- 測試：parser 表格測試、search 行為測試、CLI end-to-end、help golden snapshot、README 範例可執行性、`TestExplainParity`（在 macOS 實際執行近似 `find` 對照結果）、`TestGNUSortPipeline`（有 `gstat` 時）、read-only 原始碼守門測試、DST 測試。

## Known Limitations

依程式碼、既有報告與這一輪的實測整理。**粗體**是這一輪新發現、或是違反產品契約的項目。

**契約違反：標點被默默丟棄（這一輪實測）**

tokenizer 把 `,;()!?，、。；：！？（）` 都當成 `tPunct`，parser 在 `step()` 最後直接跳過任何 `tPunct`。因此：

| 輸入（`--explain`） | 實際解析 | 問題 |
|---|---|---|
| **`log files ! containing "ERROR"`** | `.log` AND 內容包含 `"ERROR"` | `!` 被丟掉，意思**完全相反**；實際搜尋也回傳含 ERROR 的檔案 |
| **`log files !containing "ERROR"`** | 同上 | 同上 |
| **`larger than 1GB or (smaller than 1KB and modified today)`** | `(> 1GB OR < 1KB) AND today` | 括號被丟掉，組合方式改變 |
| **`log files )`、`((log files`、`（log 檔）`** | `.log` | 不成對的括號被接受 |
| **`filename matches core.?`** | glob `"core"` | 未加引號的 glob `?` 被丟掉，句尾 `.` 被當成句號剝掉 |
| **`filename matches app-?.log`** | glob `"app-"` AND 副檔名 `.log` | 一個檔名 pattern 被拆成兩個不同條件 |
| **`filename starts with app?`** | starts with `"app"` | 條件被**放寬** |
| **`filename is core.`** | is `"core"` | 值被改寫 |
| `containing ERROR!`、`包含 錯誤！` | 內容 `"ERROR"` / `"錯誤"` | 句尾驚嘆號被丟掉（語意上多半無害，但仍屬默默修正） |

對照：`[x]`、`{x}`、`||`、`&&`、`-not`、`¬`、`非` 都會正確報錯；`NOT`、`not`、`不包含`、`except today` 會以「不支援否定」報錯。加引號的 glob（`filename matches "app-?.log"`）不受影響。既有測試與 README 範例都沒有在查詢中使用括號或驚嘆號（已 grep 確認），所以修正的相容性風險低。

**解析**

- 不支援：NOT、括號、不同類 OR、巢狀 OR、regex（內容與檔名）、檔名 ignore-case、路徑 pattern、時刻的單邊比較（`before 14:00`）、日期加時刻的比較、週（`本週`）、ISO 8601 `2026-09-28T01:00`、DD/MM、`earlier than` / `prior to` / `until`。
- 否定的錯誤訊息仍寫「**v0.1** 還不支援否定條件」／`not supported in v0.1`（實測），版本已是 0.4.0。README 的標題也仍是「Known limitations (v0.1)」。
- 大小條件互相矛盾（`larger than 10MB smaller than 1MB`）不報錯，exit 1（實測）；時間條件矛盾則 exit 2。行為不一致。
- 未加引號的中文檔名、未加引號的中文排除名稱可能被字典切開；未加引號的值延伸到空白或標點為止。
- OR 只綁定相鄰條件；`今天修改的 log 或昨天` 報錯（刻意）。`andConnectors`、`notExtWords`、`contentBoundaries` 是手動維護的清單。
- 錯誤訊息中的原文是 token 以空白接起來，不是使用者原本的字串，也沒有欄位位置。

**輸出**

- **沒有 `-0/--null`：** 檔名含換行時一個結果被拆成兩行（實測 `new\nline.log`）。
- **預設搜尋位置時路徑沒有 `./` 前綴：** 實測輸出 `-dash.log`，接到 `xargs` 等工具時可能被當成 flag。README 推薦的 `| xargs open` 遇到空白也會拆錯。
- 沒有 `--json`、`--count`、`--quiet`、`--fields`；`-l` 的時間沒有秒與時區，不適合機器解析。
- 診斷訊息只有人類可讀的雙語文字，沒有穩定的機器格式；`--confirm` 的執行計畫只有英文。
- `Report.PermissionDenied` / `OtherErrors` 沒有上限（只印前 5 筆，但全部留在記憶體）；`OtherErrors` 只印第一筆。

**走訪**

- 沒有 `--max-depth` / `--min-depth`、`--xdev`、symlink 跟隨選項。搜尋 `/` 會進入 `/proc`、`/sys`、`/dev`、macOS 的 `/System/Volumes/Data` 與 `/Volumes`、NFS / SMB 掛載點。
- 不能搜尋目錄、空目錄、symlink 本身、特殊檔案；沒有 owner / group / permission / executable 條件。
- `filepath.WalkDir` 會把一個目錄的所有 entry 讀進記憶體並排序；單一目錄有數百萬個 entry 時記憶體會尖峰。
- 搜尋位置可以是一般檔案（實測 `--dir a/app.log` 會回傳該檔），沒有文件說明。
- EACCES 與 EPERM（macOS TCC）使用同一段提示；`Operation not permitted` 顯示成 permission denied。
- TOCTOU：walk 時是 regular file、開檔前被換成 FIFO 時，內容搜尋的 `os.Open` 可能阻塞（理論風險，未實測）。

**效能**

- 有排序時收集所有符合的結果再 `sort.SliceStable`：fix round 1 量到 20 萬個檔案的 `largest 5` 約 86 MB RSS（沒排序約 3 MB）。沒有 top-N heap。
- `ignore case` 對每個 window 做 `bytes.ToLower`，不是 Unicode case folding（Kelvin 符號跨 chunk、希臘文 Σ/ς 會漏）。
- binary 偵測只看第一個 64 KB。

**平台與工程**

- 從未在 Linux 實機跑過測試；沒有 CI；沒有 fuzz target；沒有 property test；staticcheck 沒跑過。
- `make build` 沒有設定 `CGO_ENABLED=0`（只有 `make dist` 有）。目前沒有 import 會觸發 cgo 的套件，所以實際上仍是靜態，但沒有機制保證。
- `TestProductionCodeIsReadOnly` 禁止 production code import `syscall`。這是正確的安全守門，但也代表 `--xdev`（需要 `Stat_t.Dev`）、owner / group（需要 `Uid` / `Gid`）**在目前的規則下無法實作**，必須先做政策決定（見 Architecture Risks）。
- `--confirm` 沒有偵測 TTY（同樣受 `syscall` 禁令影響）。

## DevOps / SRE Gap Analysis

從實際 on-call 與維運情境看 0.4.0 能做到什麼、缺什麼。

| 情境 | 典型需求 | 0.4.0 | 缺口 |
|---|---|---|---|
| Log hunting | 「昨天 23:00 到今天 02:00 修改、包含 `ERROR` 或 `panic` 的 log」 | **可以**（時間區間 + 內容 OR + 副檔名） | regex、`不包含 healthcheck`、`.log.1` / `.gz` 輪替檔、壓縮檔內容、路徑 pattern（`*/app/*.log`）、`--count` |
| Config drift | 「`/etc` 底下今天被改過的 conf / yml」 | **可以** | 路徑條件、owner / mode（誰改的、權限被放寬）、`--json` 給 diff 工具 |
| Disk-full incident | 「`/var` 底下最大的 20 個檔案，不要跨 filesystem」 | 部分：largest + top N 可以 | **`--xdev`**、`--max-depth`、大樹記憶體（heap top-N）、目錄大小彙總（不在範圍內，見 Deferred）、`/proc` 等虛擬 FS |
| Incident timeline | 「14:00 到 14:30 之間被修改的所有檔案，依時間排序」 | 部分：時間區間 + newest 可以 | 時刻的單邊比較、ISO 8601、`-l` 缺秒與時區、oldest-first 排序、`--json` |
| Secrets / certs discovery | 「找 `.pem`、`.key`、`id_rsa`、包含 `BEGIN PRIVATE KEY` 的檔案」 | **可以**（副檔名 + 檔名 + 內容） | 權限條件（`world-readable`）、owner、跳過 `.git` 等目錄的明確 preset |
| Cleanup candidates（唯讀） | 「90 天沒改、大於 100MB 的檔案」「空檔案」「空目錄」 | 大部分可以；空檔案可用 `smaller than 1 byte` | 空目錄、目錄搜尋、`--null` 給 `xargs -0` 安全接手（刪除由使用者自己的工具做） |
| 找可執行檔 / 腳本 | 「`/opt` 底下可執行的檔案」 | 不行（實測 `executable` 報錯） | executable / permission 條件 |
| 找 symlink / 壞掉的 symlink | 「`/etc` 底下指向不存在目標的 symlink」 | 不行 | symlink 類型與 broken 判斷 |
| 自動化 / 腳本 | `if nlf -q ...; then`、`nlf --count`、`nlf --json \| jq` | 只能用 exit code 與逐行輸出 | `--quiet`、`--count`、`--null`、`--json`、穩定 schema、機器可讀診斷 |
| 大量伺服器 | 多台 Linux、不同 FS（ext4、xfs、NFS、overlayfs） | 未在 Linux 上測過 | CI 的 ubuntu job、Linux fixture、網路 FS 行為文件 |

分項評估：

- **查詢能力：** 副檔名、檔名、內容、日期時間、絕對日期比較、大小、同類 OR 已經涵蓋大部分「找檔案」的需求。最大的缺口依頻率排序是：路徑條件、NOT（特別是 `不包含`）、regex、directory / symlink / empty dir、owner / group / permission / executable、depth、mount boundary。混合類 OR 與括號在 DevOps 查詢中頻率其實不高，而且需要 AST。
- **機器輸出：** 這是目前最大的「整合」缺口。沒有 `--null` 代表 nlf 的輸出不能安全接到任何 `xargs`；沒有 `--count` / `--quiet` 代表腳本只能數行數或看 exit code。`--json` 需要先定義穩定 schema，屬於較大的設計。
- **走訪：** 沒有 depth 與 `--xdev` 是對 `/`、`/var` 做 incident response 時最痛的點。symlink 控制、特殊檔案、`/proc` 等虛擬 FS 需要清楚的預設與文件。
- **DevOps 常用排除：** 使用者目前可以明確寫 `排除 .git、node_modules`。可以提供一個**明確 opt-in** 的 preset（例如 flag `--exclude-common` 或查詢詞「排除常見目錄」），展開後的清單必須出現在 `--explain` / `--confirm`。**絕不能成為預設**。
- **效能：** 單次走訪、便宜條件先比對、內容只讀一次、未排序時提早停止都已具備。缺的是 top-N heap（排序時的記憶體）、深度剪枝、mount 剪枝。
- **平台：** 語意層面已經依 OS 處理（提示、近似指令、排除路徑大小寫），但從未在 Linux 跑過測試，這是最大的平台風險。
- **測試：** 覆蓋廣，但沒有 fuzz、property test、Linux 執行、hostile filename（換行、`-` 開頭、無效 UTF-8）的輸出測試，也沒有「標點不可被默默丟棄」的 negative test（這一輪實測發現的 bug 正好落在這個缺口）。
- **CI：** 完全沒有。每一輪的驗證都依賴人工在 macOS 上執行。

## Prioritization

排序原則，依重要性：

1. **先修契約違反。** 默默丟棄 `!` 與括號會讓結果與使用者意圖相反，比任何新功能都優先。
2. **再補驗證基礎。** CI 讓 Linux 從「只 cross-compile」變成「每次都跑測試」，也讓後續每個 milestone 的 review 成本變低。
3. **再補整合能力。** `--null`、`--count` / `--quiet` 是 flag 層的變更，不碰 parser，風險最低、腳本價值最高。
4. **再補走訪控制。** depth 不需要 `syscall`；`--xdev` 需要先決定 `syscall` 政策，所以放到 Phase B。
5. **查詢語言的擴充放在後面。** 路徑、目錄、權限、NOT、regex 各自都要新的語法與新的歧義規則，每一項都是獨立 milestone。
6. **AST 只在真正需要時做。** 目前的 `Query + AnyOf` 模型足以支援 Phase A–C 的全部項目（包括「AND NOT 內容」）；只有不同類 OR、括號、一般 NOT 需要 AST。

每個 milestone 的完成標準都一樣：`make check`、`go test -race ./...`、`go test -count=10 ./...` 通過；新增 regression test；README、help（含 golden）、`--explain` 同步；有 Backward Compatibility 段落；單獨一個 commit，可以獨立 revert。

## Phase A — High-value / Low-risk

目標：不動 query model、不動 search engine 的核心結構、不需要 `syscall`。每一項都是可以獨立 review 的 milestone。

**A1 — 標點嚴格化（reserved punctuation）** ← 建議的第一個 milestone（見下方說明）

- 括號 `(`、`)`、`（`、`）` 在引號外一律報錯：「目前不支援括號」並提示改寫或加引號。
- 驚嘆號 `!`、`！` 在引號外一律報錯：可能代表 NOT，而 NOT 目前不支援。
- 問號 `?`、`？`：只允許在整個查詢的最後（句尾問號，例如 `哪些 log 檔今天改過？`），其他位置報錯。緊接在未加引號的值後面（`app?`、`core.?`）一律報錯，提示加引號。
- 未加引號的**檔名值**後面緊接句號（`filename is core.`）時報錯，提示加引號；目前會被默默剝成 `core`。
- 同時把錯誤訊息裡過時的「v0.1」拿掉（`negative conditions are not supported` / 「還不支援否定條件」）。
- 預計版本：**0.4.1**（修正錯誤的接受行為；以前會被接受的查詢改為 exit 2）。

**A2 — CI：GitHub Actions**

- `ubuntu-latest` 與 `macos-latest` matrix：`make check`、`go test -race ./...`、`make dist`、驗證 `SHA256SUMS`、確認 `nlf-*-linux-*` 是靜態 ELF（`file` 或檢查沒有 `PT_INTERP`）。
- 只在 `tools/nlf/**` 變更時觸發；不 publish、不需要 secrets、`permissions: contents: read`。
- 第一次在 Linux 上跑 759 個測試；預期可能暴露 `TestExplainParity`（GNU find）、大小寫敏感 FS、`/tmp` 不是 symlink 等差異，修正屬於這個 milestone 的一部分，但**不得為了變綠而放寬測試**。

**A3 — `-0` / `--null`**

- 每個結果以 NUL 結尾，不輸出換行；與 `-l` 同時使用時報錯（`-l` 是給人看的）。
- stderr 不受影響；exit code 不變。
- README 改成推薦 `nlf -0 … | xargs -0 …`，並說明預設輸出遇到換行檔名的限制。

**A4 — `--count` 與 `-q` / `--quiet`**

- `--count`：只在 stdout 印出一個十進位整數與換行（符合的數量，套用數量上限之後）；0 筆時印 `0`、exit 1。
- `-q` / `--quiet`：stdout 不輸出，找到第一個就停止（沒有排序時），exit 0 / 1 / 2 的意義不變；stderr 的「沒有找到」提示也省略，但錯誤與權限警告仍寫 stderr。
- 兩者互斥，也和 `-l`、`-0` 互斥；和 `--explain` 同時使用時報錯（`--explain` 不搜尋）。

**A5 — `--max-depth N` / `--min-depth N`**

- 與 `find` 相同的深度定義：搜尋位置本身是 0，它底下的檔案是 1。`--max-depth` 在超過深度的目錄 `SkipDir`，不進入；`--min-depth` 只過濾結果。
- `N` 必須是非負整數；`min > max` 報錯；只能以 flag 提供（不新增自然語言詞彙，避免和「最多 N 個」衝突）。
- `--explain` / `--confirm` 顯示深度，近似指令加上 `-maxdepth` / `-mindepth`。

**A6 — Top-N heap**

- 有排序且有數量上限時，用大小 N 的 heap 保留結果，記憶體從 O(符合數) 降到 O(N)；沒有上限時維持現狀。
- 輸出順序與同分規則（依路徑）必須和現在完全相同，用 property test 對照舊的 `sort.SliceStable` 結果。

**A7 — Fuzz 與 hostile filename 測試**

- `FuzzParse`（不 panic、同輸入同輸出、`Explain` 不 panic、成功時 `FindCommand` 可產生）、`FuzzTokenize`、`FuzzScanTerms`（與整檔 `bytes.Contains` 對照，隨機切 chunk）、`FuzzShellQuote`。
- CLI fixture：換行、`-` 開頭、空白、無效 UTF-8、很長的檔名、中文檔名。
- 加入 corpus 到 `testdata/fuzz`；CI 只跑 seed corpus（`go test` 預設），長時間 fuzz 由人工觸發。

**為什麼 A1 是標點嚴格化**

- **價值：** 它修的是契約違反，不是缺少的功能。`log files !containing "ERROR"` 目前回傳的正好是使用者**不要**的檔案；`filename starts with app?` 默默放寬條件。這比任何新 flag 都嚴重。
- **頻率：** 熟悉 `find` / shell 的維運人員很自然會寫 `!`、括號與未加引號的 glob（`core.?`、`app-?.log`）。
- **風險：** 只會把「以前被接受」的查詢變成 exit 2，不會讓任何查詢的結果變多或改變；既有測試與 README 範例都沒有使用這些標點（已 grep 確認）。
- **範圍：** 只動 tokenizer / parser 的標點處理與錯誤訊息，不動 `Query`、search、explain 的結構；不需要 AST、不需要重寫 tokenizer、不需要 `syscall`。
- **依賴：** 沒有前置依賴；而且它是 Phase C / D（NOT、括號）的前提：在支援之前先把這些符號保留下來、明確報錯，之後才能安全地賦予意義。
- **替代方案：** 如果希望第一個 milestone 是新能力，A3（`-0`）是次佳選擇；兩者互不依賴，順序可以對調，但 A1 應該在下一個 release 之前完成。

## Phase B — Operational Depth

目標：補齊 incident response 需要的走訪控制與輸出格式。部分項目需要先做政策決定。

- **B0 — `syscall` 政策決定（文件，不寫程式）：** 是否允許在單一、受測試限制的檔案（例如 `internal/search/stat_unix.go`）中讀取 `info.Sys().(*syscall.Stat_t)` 的 `Dev`、`Uid`、`Gid`，而 `TestProductionCodeIsReadOnly` 改成「只允許這個檔案 import `syscall`，而且只允許使用 `Stat_t` 的欄位」。沒有這個決定，B2、B6 不能開始。
- **B1 — 路徑條件：** `路徑包含 nginx/`、`path contains /app/`、`path matches "*/conf.d/*.conf"`；比對相對於搜尋位置的路徑，永遠用 `/` 分隔，大小寫敏感；和檔名條件分開，不會互相推導。
- **B2 — `--xdev`：** 不進入不同 device 的目錄；搜尋位置本身的 device 為基準；`--explain` 顯示，近似指令加 `-xdev`。依賴 B0。
- **B3 — `--json`：** 每行一個 JSON 物件（NDJSON），欄位固定（`path`、`size`、`mtime`（RFC 3339，含時區與奈秒）、`type`），帶 `schema` 版本；和 `-l`、`-0`、`--count` 互斥。先寫 schema 文件與 golden test 再實作。
- **B4 — `--fields` 或 `-l` 格式改進：** 顯示秒與時區；或讓 `-l` 維持不變、新增 `--time-format=iso`。需要和 B3 一起決定，避免兩套欄位名稱。
- **B5 — 目錄、空目錄、symlink 類型：** `找目錄`、`directories named logs`、`空目錄`、`empty files`（等於 size == 0 的別名）、`symlinks`、`broken symlinks`。預設仍然只找 regular file，類型必須明確寫出。
- **B6 — 權限、executable、owner / group：** executable 與 mode 只需要 `fs.FileMode`，可以先做；owner / group 依賴 B0，名稱解析要避免 cgo（`os/user` 在 `CGO_ENABLED=0` 下會讀 `/etc/passwd`，但不支援 LDAP / NSS，必須在文件中說明，或只接受數字 uid / gid）。
- **B7 — 明確 opt-in 的常用排除：** 例如 `--exclude-common` 或查詢詞「排除常見目錄 / exclude common dirs」，展開成固定清單（`.git`、`node_modules`、`vendor`、`dist`、`build`、`.cache`、`__pycache__`、`.venv`、`target`），並完整列在 `--explain` / `--confirm`。清單內容寫進文件與測試；**永遠不會預設開啟**。
- **B8 — 診斷改進：** EACCES / EPERM 分開提示；`Report` 設上限並顯示總數；`OtherErrors` 顯示分類；大小矛盾在 parse 時報錯（與時間一致）；`--json` 模式下 stderr 也可以是 NDJSON 診斷（`{"level":"warn","kind":"permission","path":…}`）。
- **B9 — 虛擬 FS 與特殊路徑文件：** 在文件中定義 `/proc`、`/sys`、`/dev`、NFS、macOS firmlink 的行為與建議寫法（搭配 B2 與 A5），並加 Linux-only 的整合測試（在 CI 的 ubuntu job 上）。

## Phase C — Advanced Querying

目標：擴充查詢語言，但仍然使用 `Query + AnyOf` 模型，不做 AST。

- **C1 — 內容 NOT：** `不包含 "healthcheck"`、`without "DEBUG"`、`not containing "x"`。模型上是 `Query.NotContents []string`：全部 AND NOT。和內容 OR / AND 在同一次讀檔中判斷；binary 檔的處理必須明確定義（建議：binary 檔不符合任何內容條件，包括 NOT）。`except` 與 `不要` 的既有歧義規則保留。
- **C2 — Regex：** `內容符合 regex "err(or)?\s+\d+"`、`filename regex "^app-\d+\.log$"`。一律使用 Go RE2，必須有 `regex` 關鍵字與引號，不從一般文字推測；pattern 在 parse 時編譯，錯誤 exit 2。跨 chunk 的比對需要重新設計（line-based 或限制最大 match 長度），這是這一項最大的風險。
- **C3 — 檔名 ignore-case：** 明確的語法（例如 `檔名不分大小寫`、`name (ignore case)`），和內容的 `ignore case` 分開，不能互相影響。
- **C4 — 日期加時刻與 ISO 8601：** `after 2026-09-01 14:00`（mtime >= 該瞬間）、`2026-09-28T01:00`、`2026-09-28T01:00:00+08:00`（有時區時使用該時區）。時刻沒有日期時仍然報錯。
- **C5 — 其他 NOT：** 檔名、副檔名、時間、大小的 NOT，模型上各自是一個 `Not…` 欄位；只允許 NOT 單一條件或同類 OR 群組，不允許 NOT 套在混合條件上。
- **C6 — 英文同義詞：** `earlier than`、`prior to`、`or earlier`、`or later`、`until`（先定義 `until` 含不含當天）。

## Phase D — Architecture / Long-term

- **D1 — AST migration：** 只有在決定支援不同類 OR、括號或任意 NOT 時才啟動。做法依 boolean-or 報告的規劃：parser 已經是「每個條件先 parse 成 sub-query 再合併」，可以產生 `And` / `Or` / `Not` / 葉節點；`Query` 保留為「AND of leaves + same-kind OR」的正規形式，search 先判斷 AST 是否能降成 `Query`，能的話走現在的快路徑。explain 需要遞迴的樹狀顯示。
- **D2 — 不同類 OR 與括號：** 依賴 D1。在那之前，A1 讓括號明確報錯。
- **D3 — Tokenizer 保留 span：** 每個 token 記錄原文的 byte offset，錯誤訊息可以顯示原文片段與 `^` 位置；也讓「值緊接標點」這類判斷不再依賴 `spaceBefore` 等旗標。
- **D4 — Search 成為 predicate pipeline：** 條件依成本排序（name → stat → content），讓新增條件類型不需要改 `Run` 的主流程。先量測再決定。
- **D5 — 平行內容掃描（可選）：** 只有在量測證明內容搜尋是瓶頸時才做，而且輸出必須依原本的 lexical 順序（例如 bounded worker pool + 依序 emit）。
- **D6 — Unicode case folding：** 如果需要真正的 case-insensitive 內容搜尋（`unicode.SimpleFold` 或 `strings.EqualFold` 的串流版本），並處理長度改變的字元跨 chunk 的問題。

## Deferred Features

| 功能 | 延後原因 | 重新考慮的條件 |
|---|---|---|
| 特殊檔案（FIFO / socket / device）搜尋 | 使用頻率低；需要避免開啟這類檔案 | B5 完成後有明確需求 |
| 週（`本週`、`上週`） | 一週的起點需要先定義；`last week` 已有相對意義 | 有使用者需求並決定 ISO 週（週一）或其他 |
| 壓縮檔 / `.gz` 內容 | 改變「內容」的定義，binary 判斷也要重做 | 在 C2 之後，並明確需要 `--decompress` 類 flag |
| `.gitignore` awareness | 規則複雜（巢狀、negation、global ignore），預設開啟會違反契約 | 只考慮 opt-in，並且 `--explain` 能列出被忽略的原因 |
| 目錄大小彙總（`du`） | 不同的輸出模型與效能特性 | 另開產品討論 |
| 設定檔 / 自訂別名 | 同一查詢在不同機器結果不同 | 只有在可以用 `--explain` 顯示來源、並能用 flag 關閉時 |
| 平行走訪 | 難以保持 deterministic 順序；目前沒有量測資料 | D4 與量測之後 |
| Unicode case folding | 影響範圍小，實作與測試成本不小 | 有實際 bug 回報 |
| TTY 偵測（`--confirm`） | 需要 `syscall` 或 `x/term` | B0 政策決定之後 |
| Windows 支援 | 不在一等平台內；路徑、權限、symlink 語意都不同 | 另行決定 |

## Rejected Ideas

- **預設套用常用排除目錄**：默默縮小範圍，使用者看不到哪裡被跳過。改為 B7 的明確 opt-in。
- **任何會修改檔案系統的動作**（`-delete`、`-exec`、移動、改權限）：違反 read-only。nlf 只負責「找」，動作交給使用者自己的工具，A3 的 `-0` 讓這件事可以安全地做。
- **自動 sudo 或提權重試**：違反契約。
- **看不懂時用 LLM、模糊比對或「最可能的意思」**：違反 deterministic 與「不猜」。
- **為了速度呼叫 `find`、`grep`、`rg`、`fd`**：違反 Go-native traversal 與不執行外部程式；也會讓 macOS / Linux 行為不一致。
- **依 locale 猜日期格式、接受兩位數年份**：有歧義一律報錯是既定規則。
- **Watch mode、daemon、索引資料庫**：需要寫入快取，也不是一次性查詢工具。
- **把 `?`、`!`、括號等標點「修正」成最可能的意思**：與 A1 的方向相反；在支援之前一律明確報錯。

## Architecture Risks

- **`syscall` 禁令與 Phase B 衝突：** `--xdev`、owner / group、TTY 偵測都需要 `syscall`（或以 `reflect` 讀取 `info.Sys()`，那只是繞過守門，**不建議**）。必須先做 B0 的政策決定，並把守門測試改成白名單，而不是移除。
- **Query struct 持續膨脹：** 每加一種條件就多一個欄位與一段 `match…`、`Conditions`、`FindCommand` 的程式。Phase C 結束時大約會有 8–10 種條件類型。這是 D1 / D4 的觸發條件之一，但不應該為了預防而提早做 AST。
- **Explain 與 search 的一致性：** 每種新條件都要同時更新 search、`Conditions`（`--explain` / `--confirm`）、`FindCommand`（兩種 OS）、help golden、README。`TestExplainParity` 只在 macOS 上執行，而且只涵蓋部分查詢；A2 之後應該讓它在 ubuntu 上也跑 GNU find。
- **CLI flag 互斥矩陣：** A3–A5、B2–B4 會新增許多 flag。建議在 A3 就把 flag 解析與互斥檢查集中在一個表格驅動的函式裡，避免每個 milestone 各寫一段 `if`。
- **`--json` schema 是長期承諾：** 一旦發布就要維持相容；欄位名稱、時間格式、數字型別都要在 B3 一次定好。

## Parser Risks

- **標點被默默丟棄（A1 要修）：** `step()` 最後 `if t.kind == tPunct { p.pos++ }` 會吞掉任何標點，包括語意上重要的 `!`、`(`、`?`。修正方向是讓「有意義的標點」在 tokenizer 或 parser 層明確報錯，而不是擴大 filler。
- **句尾句號剝除：** `classifyASCII` 會把 word 結尾的 `.` 剝掉當成句號；對檔名值、glob 值而言這會改變值本身（`core.` → `core`）。
- **手動維護的詞彙清單：** `andConnectors`、`notExtWords`、`contentBoundaries`、`fillers` 漏掉一個詞就會造成報錯或誤解；每新增一個關鍵字都可能影響「任意英數字 + files = 副檔名」的規則與 OR 的連接詞判斷。
- **中文斷詞：** 字典最長匹配，新增一個中文關鍵字可能讓既有的內容文字或排除名稱被切開（fix round 1 的同類問題）。每次新增中文詞都要跑既有的中文內容與排除測試。
- **新語法的歧義：** 路徑（`/` 同時用於路徑與日期 `9/28`）、regex（引號內的反斜線）、NOT（`不要`、`except` 既有規則）、`before` + 數字（相對時間 vs 年份）都已有歧義規則；新增語法時必須先寫歧義表，再寫程式。
- **錯誤訊息的原文：** token 以空白重組，不是原文；D3 之前，新錯誤訊息要避免讓使用者誤以為自己輸入了空白。

## Filesystem Risks

- **虛擬 FS：** `/proc` 的檔案大小多為 0、內容是動態產生；`/proc/kmsg` 等檔案在有權限時讀取會阻塞；`/sys` 有大量檔案。內容搜尋搜 `/` 時風險最高。建議在文件中要求排除或使用 `--xdev`（B2），並在 B9 加 Linux 測試。
- **特殊檔案與 TOCTOU：** 目前只對 regular file 開檔，但 walk 與 open 之間檔案可能被替換成 FIFO，`os.Open` 可能阻塞。可行的緩解是開檔後再 `f.Stat()` 確認仍是 regular file（仍可能在 open 本身阻塞；完全避免需要 `O_NONBLOCK`，也就是 `syscall`）。
- **網路 FS：** NFS / SMB / sshfs 的 `ReadDir` 與 `Stat` 延遲高、可能掛住；mtime 精度與時鐘可能和本機不同。沒有 timeout 機制；只能在文件中建議縮小範圍與 `--xdev`。
- **mtime 精度：** ext4 / xfs / APFS 是奈秒，HFS+ 是 1 秒，FAT 是 2 秒，部分 NFS 設定是秒。半開區間的邊界測試都在 APFS 上跑過，其他 FS 上的邊界檔案可能落在不同側。
- **大小寫：** macOS APFS 預設不分大小寫、Linux ext4 / xfs 區分。檔名與路徑比對是 nlf 自己的規則（區分大小寫），排除路徑依檔案系統判斷；新功能（路徑條件）必須明確選擇其中一種並寫進文件。
- **權限與安全模組：** Linux 上 SELinux / AppArmor 可能在 `ReadDir` 或 `Open` 回傳 EACCES；macOS TCC 回傳 EPERM。兩者目前被同樣處理。
- **iCloud / dataless 檔案：** 內容搜尋可能觸發下載（fix round 1 列為人工驗證項目，尚未驗證）。
- **非常大的單一目錄：** `os.ReadDir` 一次讀入並排序；數百萬 entry 時記憶體尖峰。改為串流會失去 lexical 順序（deterministic），所以不建議改，只在文件中說明。

## Performance Strategy

- **量測先於最佳化。** 在 A6 之前先建立可重現的 benchmark fixture（例如 20 萬個檔案、深度 10），量測 RSS、`Lstat` 次數（`d.Info()`）、`Open` 次數、總時間，並寫進報告。
- **保持成本順序：** 名稱 / 副檔名（不 Stat）→ 深度（A5，不 Stat）→ `d.Info()`（大小、mtime、mode、B6 的 owner）→ 內容（開檔）。新條件必須放在正確的層級，並有測試確認「不符合前面條件的檔案不會被 Stat / Open」（沿用 `TestFilenameBeforeContent` 的做法）。
- **剪枝：** `--max-depth`、`--xdev`、排除目錄都在目錄層級 `SkipDir`，不進入。
- **提早停止：** 沒有排序時達到上限即 `SkipAll`；`--quiet` 找到第一個就停止；`--count` 不能提早停止（除非有上限）。
- **排序記憶體：** A6 的 heap 讓 top-N 為 O(N)；沒有上限的排序仍是 O(符合數)，在文件中說明。
- **內容掃描：** 維持單次讀取、所有 term 一起比對、滿足即停止。regex（C2）要避免對整個 window 反覆掃描；`ignore case` 的 `bytes.ToLower` 每個 chunk 都配置新記憶體，可在 A6 / D6 時一起改成重用 buffer。
- **不做平行化，直到量測證明需要**（D5），而且輸出順序不能改變。

## Testing Strategy

- **Unit：** parser 表格測試（每種新語法都有正向、反向、歧義三組）、`Match` 函式、時間與 DST。
- **Negative / strictness：** A1 新增「每一個 `punctChars` 字元在每一個位置」的表格測試：只有明確允許的位置可以成功，其他一律 exit 2。之後每新增一種語法，都要加「看起來像但不支援」的報錯測試。
- **Integration（search）：** `t.TempDir()` fixture，涵蓋排除、symlink、權限、FIFO、空檔案、深度、hostile filename。
- **CLI end-to-end：** exit code、stdout / stderr 分離、flag 互斥矩陣、`--explain` 不搜尋（沿用既有測試）、`--confirm` 只接受 `y` / `Y`。
- **Golden：** help snapshot、`--explain` 輸出、B3 的 JSON schema。
- **Parity：** `TestExplainParity` 在 macOS（BSD find）與 ubuntu（GNU find）都要跑；`TestGNUSortPipeline` 在 ubuntu 上不需要 `gstat`。
- **Race 與重複：** `-race`、`-count=10`（CI 至少跑 `-race`）。
- **Fuzz（A7）：** `FuzzParse`、`FuzzTokenize`、`FuzzScanTerms`、`FuzzShellQuote`；seed corpus 納入版本控制。
- **Property：** A6 的 heap vs 完整排序；`Parse` 的 deterministic（同輸入、同 `now` 兩次結果相同）；「加上一個 AND 條件，結果集合只會變小」。
- **Hostile filenames 與 Unicode：** 換行、tab、`-` 開頭、無效 UTF-8、NFC / NFD（macOS 的檔名正規化）、全形字元、emoji、很長的路徑。
- **Read-only 守門：** 保留 `TestProductionCodeIsReadOnly`；B0 之後改成白名單，不得移除。
- **不得為了變綠而放寬測試**；平台差異要用明確的 `runtime.GOOS` 分支並寫出原因。

## Linux Strategy

- **A2 是第一步：** 在 `ubuntu-latest` 上跑完整測試，把「從未在 Linux 執行」變成每次都執行。
- **GNU 工具：** 近似指令已經有 GNU 版本；在 ubuntu 上讓 `TestExplainParity` 與 sort pipeline 用真的 GNU find / stat 驗證。
- **大小寫敏感 FS：** `TestExcludePathCaseFollowsFileSystem` 會依檔案系統判斷期望值，需要在 ext4 上實際通過一次。
- **虛擬 FS 與 mount：** B2（`--xdev`）與 B9 的文件與測試；在 CI 上可以用 `/proc` 做唯讀的整合測試（例如 `--dir /proc --max-depth 1` 不 panic、不阻塞）。
- **權限：** CI runner 通常是非 root 使用者，可以測 EACCES；root 下的行為（權限測試會被略過）要在測試中明確 `t.Skip` 並寫原因。
- **發行：** `linux/amd64`、`linux/arm64` 靜態 ELF；CI 檢查沒有動態連結。
- **overlayfs / container：** 在文件中說明 container 內搜尋 `/` 的建議（排除 `/proc`、`/sys`，或使用 `--xdev`）。

## macOS Strategy

- **保持目前的一等支援：** 開發機仍是 macOS；CI 的 `macos-latest` 是 arm64，Intel 版本由 `make dist` cross-compile。
- **TCC：** EPERM 與 EACCES 分開提示（B8）；「授權 Full Disk Access 後是否能讀」「Desktop / Documents / Downloads 首次存取的對話框」仍需人工驗證，列在每次 release 的 manual checklist。
- **firmlink 與 `/Volumes`：** 搜尋 `/` 會經過 `/System/Volumes/Data` 並進入外接磁碟與網路磁碟；`--xdev`（B2）要在 macOS 上驗證 firmlink 的 device 行為。
- **APFS 不分大小寫與 Unicode 正規化：** 檔名比對是 nlf 自己的規則（區分大小寫，逐 byte 比對）；NFD 檔名與 NFC 查詢可能不相符，需要在 A7 加測試並在文件中說明。
- **iCloud dataless 檔案：** 內容搜尋可能觸發下載；在文件中提醒，並列入人工驗證。
- **Gatekeeper / quarantine：** README 已說明；release 不做 notarization（需要 Apple 帳號與網路，另行決定）。

## CI Strategy

A2 的具體內容：

- Workflow：`.github/workflows/nlf-ci.yml`，觸發條件為 `pull_request`，以及推到 `main`／`feat/**` 的 `push`，且路徑是 `tools/nlf/**` 或 workflow 本身；另可 `workflow_dispatch`。
- `permissions: contents: read`；不使用 secrets；不 publish 任何東西。
- Matrix：`ubuntu-latest`、`macos-latest`；Go 版本固定為 `go.mod` 的版本（`actions/setup-go` 搭配 `go-version-file: tools/nlf/go.mod`）。
- Steps：`make fmt-check`、`make vet`、`go test -race ./...`、`go test -count=10 -shuffle=on ./...`、`make build`、`make dist`、在 `bin/` 執行 `sha256sum -c SHA256SUMS`（macOS 用 `shasum -a 256 -c`）、確認 linux binary 是靜態（例如 `file` 輸出含 `statically linked`）。完整步驟（skip guard、`CGO_ENABLED=0`、`scripts/ci-smoke.sh`、工作目錄乾淨檢查）見 README CI 小節與 workflow。
- 第三方 action 固定到 commit SHA；只用 `actions/checkout`、`actions/setup-go`。
- 之後（非 A2 範圍）：staticcheck（需要下載工具，另外決定）、定期的長時間 fuzz（人工觸發）、release workflow（見下節）。

## Release Strategy

- **Semantic versioning（0.x）：** 新查詢能力或新 flag → minor；只修正錯誤行為 → patch。A1 建議 **0.4.1**；A2 不改版本（只有 CI）；A3–A5 可以合併成 **0.5.0**（「pipe 與走訪控制」），A6、A7 不影響行為可以跟著任一版。
- **每個 release：** 更新 `main.go` 的 `version`、help golden、README 裡的 binary 名稱；`make check`、`make dist`、`SHA256SUMS`；報告中寫明 Backward Compatibility；建立 annotated tag `tools/nlf/vX.Y.Z`。
- **Tag 不移動、不 force push**；發現問題就發下一個 patch。
- **Release 產物：** 目前只在本機 `bin/`（gitignored）。是否透過 GitHub Releases 發布 binary 與 checksum，需要另外決定（需要 `contents: write` 權限的 workflow）。
- **行為變更要明確：** 任何「以前被接受、現在報錯」或「結果改變」的變更，要在 README 與報告中逐條列出（沿用 0.4.0 對 `N 月以前` 的做法）。
- **1.0 的條件：** Phase A 完成、CI 在兩個平台都綠、`--json` schema 定案（B3）、Linux 與 macOS 的人工驗證清單完成。

## Success Criteria

這份 roadmap 的每個階段完成時，應該能檢查以下條件：

- **A1：** 引號外的 `( ) （ ） ! ！` 在任何位置都 exit 2；非句尾的 `? ？` 與緊接在未加引號值後面的 `?`、句號都 exit 2；加引號的相同文字仍可使用；錯誤訊息沒有「v0.1」；這一輪 Known Limitations 表格中的每個例子都有 regression test；759 個既有測試全部通過。
- **A2：** `main` 上每個 `tools/nlf/**` 的變更都在 ubuntu 與 macos 上跑 `make check`、`-race`、`make dist` 並通過；README 的「沒有在 Linux 實機跑過測試」可以刪除。
- **A3–A5：** `nlf -0 … | xargs -0` 能正確處理換行與空白檔名；`--count` / `--quiet` 的 exit code 與既有定義相同；`--max-depth 0` / `1` 與 `find -maxdepth` 結果相同（parity test）。
- **A6：** 20 萬個檔案的 `largest 5` RSS 接近未排序的情況；輸出與舊實作逐行相同。
- **A7：** fuzz seed corpus 在 CI 通過；hostile filename 測試涵蓋換行、`-` 開頭、無效 UTF-8、NFD。
- **Phase B：** 在 Linux 上對 `/` 做 `--xdev --max-depth 3` 的 largest 查詢，不進入 `/proc`、不阻塞；`--json` 有 schema 文件與 golden test；owner / group 的實作通過白名單式的 read-only 守門。
- **Phase C：** 每種新語法都有歧義表與「看起來像但不支援」的報錯測試；`不包含` 在 binary 檔上的行為有文件與測試。
- **Phase D：** AST 導入前後，所有既有查詢的 `Query` 形狀與搜尋結果完全相同（對照測試）。
- **全程：** 產品契約的 16 條沒有任何一條被放寬；`TestProductionCodeIsReadOnly` 仍然存在並通過；沒有新增第三方依賴（除非有書面理由並經過同意）。
