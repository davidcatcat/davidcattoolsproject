# nlf A6：Top-N heap（有數量上限的排序只保留 N 筆）

日期：2026-09-28
分支：`feat/nlf-roadmap-a6-topn-heap-20260928`（從 main `5cdd567` 建立；**未 merge 到 main**）
版本：維持 0.4.0（沒有 bump、沒有 tag）

**A6 只改效能與記憶體，沒有任何使用者可見的變更。** stdout、stderr、exit code、`--explain`、`--help`、`--version` 都與 baseline（main `5cdd567`）byte-identical，見下方對照。

## 舊演算法

`largest` / `newest`（有或沒有數量上限）：

1. 走完整棵樹，把每一筆符合條件的 `Result` 收集到 slice
2. `sort.SliceStable` 完整排序
3. 截前 N 筆

符合數為 M 時，記憶體 O(M)、排序 O(M log M)。`最大的 5 個` 在 20 萬個檔案上會保留 20 萬筆。

## 新演算法

只有在 `q.Sort` 是 `SortLargest` 或 `SortNewest`，**而且** `q.Limit > 0` 時，`newTopNFor(q)` 才回傳 bounded collector；其他情況回傳 nil，走原本的程式。

- **`SortNone` + 數量上限：** 找到 N 個就 `fs.SkipAll` 提早停止，完全沒動。
- **排序但沒有上限：** 仍然是收集全部 → 排序，完全沒動。

**共用 comparator（`internal/search/search.go`）：**

```go
func better(a, b Result, order query.SortOrder) bool {
	switch order {
	case query.SortLargest:
		if a.Size != b.Size {
			return a.Size > b.Size
		}
	case query.SortNewest:
		if !a.ModTime.Equal(b.ModTime) {
			return a.ModTime.After(b.ModTime)
		}
	}
	return a.Path < b.Path
}
```

`sortResults`（完整排序）與 heap 都只用這一個定義，內容就是 A6 之前 `sortResults` 裡的 less 函式。

**Tie-break：** 主鍵相同時依 `Path` 字串遞增（位元組順序），規則不變。

- 每個路徑在一次 Run 中只會出現一次（`WalkDir` 對每個路徑只呼叫一次，子路徑由 `filepath.Join` 產生；目錄樹裡的 symlink 不跟隨），所以 (主鍵, Path) 是嚴格全序，stable 與否不影響結果。
- `FileInfo.ModTime()` 是 `time.Unix(sec, nsec)`，沒有 monotonic reading，所以 `Equal` / `After` 一致。有測試確認這點。

**Heap invariant（`container/heap`）：** root 是保留集合中「最差」的一筆，`Less(i, j) = better(h[j], h[i])`。

- largest：size 最小；同 size 時 path 最大
- newest：mtime 最舊；同 mtime 時 path 最大

**更新規則：**

- 保留數 < N 時直接 push。
- 否則只在新結果 `better(r, h[0])` 時取代 root 並 `heap.Fix(h, 0)`。
- heap 永遠最多 N 筆，沒有另一份完整清單。

**輸出：** 走訪結束後取出保留的筆數，用同一個 comparator 排序後依序 emit，不依 heap pop 順序輸出。

**初始容量 `min(N, 1024)`：** parser 允許的 Limit 上限是 `MaxInt32`。如果直接配置 N，`top 2147483647 largest` 會嘗試配置約 103 GB 而 crash；舊版只會隨符合數成長。現在 heap 只隨實際結果數成長，行為與舊版相同。

**沒有任何提前剪枝：** 即使某個檔案不可能贏過 root，照樣會 Stat、比對內容。開檔／讀取錯誤會進入 stderr 並影響 exit code，所以被 Stat 與開啟的檔案與以前完全相同。

## Complexity

| 情況 | 記憶體 | 時間 |
|------|--------|------|
| 舊版（符合數 M） | O(M) | 排序 O(M log M) |
| **A6，有上限 N** | **heap O(min(N, M))** | 走訪時更新 O(M log N)，最後排序 O(N log N) |
| 排序但沒有上限（不變） | O(M) | O(M log M) |
| 未排序 + 上限（不變） | O(1) 額外記憶體 | 找到 N 個就停止 |

## 剩下的風險

- `heap.Push` 每次 push 包一次 `any`。N 很大而且 ≥ M 時，總配置比沒有上限的路徑多約 4%（QA：226.8 vs 218.2 MiB），但 RSS 與時間沒有退步。可以改成 `append` + `heap.Fix(len-1)` 避免，本輪依 spec 保留。
- 「直接配置 N」這個 mutant 在完整測試中是靠 OS 砍掉測試程式（OOM）才失敗，不是乾淨的斷言；單獨跑 `TestNewTopNFor` 時是斷言失敗。
- 20 萬檔案的 RSS 量測只在本機（macOS）做過，CI 不跑。Linux 的記憶體行為預期相同（同一份 Go 程式），但沒有量測數字。
- **沒有做：** 平行走訪、worker pool、串流排序輸出、external sort、走訪改寫、A7 fuzz、Phase B。
- 產品原則不變：read-only、deterministic、production 不執行 shell、不 import `os/exec`、不連網路、不用 LLM、不用 sudo、沒有新增第三方依賴（`container/heap` 是標準函式庫）、macOS／Linux 語義相同。
